# Project Doctor：平台技术栈与代码组织

日期：2026-10-02

状态：技术栈与组织原则已获用户确认；本文为落实这些决策的书面设计，待复核。尚未进入产品代码实现。

产品范围遵循 [整体设计](2026-09-30-backend-performance-diagnosis-agent-design.md)：首版诊断慢查询／有代价的全表扫描、N+1、深分页。本文规定平台自身架构，不规定待诊断项目的语言、ORM 或数据库。

## 1. 决策摘要

采用 **Python 核心 + MCP + AGH，平台业务数据存储使用 MySQL**。

首要目标是层次清晰、耦合低、修改方便和人可读。实现采用一个 Python 项目中的明确模块边界，首版不拆微服务。AGH 负责模型与工具调用循环；Python 负责实际业务能力、实验状态、资源约束和证据校验。MCP 是调用入口，不承载诊断业务规则。

原始 trace、日志、执行计划等制品保存到独立文件目录，MySQL 保存业务数据、证据索引和文件位置。平台 MySQL 与待测项目数据库分别配置和管理；恢复待测环境不得影响平台记录。

## 2. 技术选择与适用边界

| 部分 | 选择 | 责任 |
| --- | --- | --- |
| 业务核心 | Python | 场景、实验、判定、报告和恢复流程 |
| 数据合同 | Pydantic | 校验字段、类型、单位和格式版本；不替代根因验证 |
| Agent 执行 | AGH + 可配置诊断模型 | 假设生成、实验选择、工具调用及会话记录 |
| 工具接入 | 官方 Python MCP SDK | 结构化输入输出；调用 Python 业务流程 |
| 平台存储 | MySQL | 任务、场景版本、实验、假设、结论、证据索引与状态记录 |
| 原始证据 | 文件制品目录 | 保存原始数据，通过索引与内容校验值关联 |
| 隔离环境 | Docker Compose + 项目／数据库专用恢复实现 | 启动、健康检查、资源隔离、恢复基线 |
| 场景请求 | httpx | 执行业务请求序列并检查结果 |
| 负载实验 | 按需接入 k6 | 在需要并发或到达率控制时执行受限负载 |
| 报告 | JSON + HTML | 可核对的数据输出和人可读报告 |
| 开发检查 | pytest、Ruff、类型检查 | 验证关键规则、模块边界及失败行为 |

上述为选型，尚不表示实际集成通过。AGH、MCP SDK、数据库驱动和 Python 版本在最小接入验证后锁定；不凭未验证的版本组合安装产品依赖。MySQL 数据访问与迁移实现集中在存储模块，后续实现计划再确定具体库。

首版不增加第二个 Agent 主循环，不引入 LangGraph 管理同一诊断循环。报告先使用 HTML，不预建独立前端、消息队列或通用插件框架。

## 3. 五部分职责与依赖

| 部分 | 做什么 | 不承担什么 |
| --- | --- | --- |
| 接入入口 | 接收 MCP 调用、校验参数、返回结构化结果 | 不写诊断规则，不直接操作容器或数据库 |
| 业务流程 | 组织步骤，检查任务状态和预算，安排恢复 | 不解析数据库私有格式，不重复实现诊断判据 |
| 功能模块 | 各自实现环境、场景、实验、诊断和报告规则 | 不依赖 AGH 会话对象，不散落外部 SDK 调用 |
| 外部实现 | 操作 MySQL、Docker、HTTP 和观测工具，转换外部数据 | 不决定问题是否已验证，不反向调用业务流程 |
| 数据定义 | 定义模块间的数据含义与版本 | 不执行请求、SQL 或模型调用 |

接入入口调用业务流程；业务流程调用功能模块和明确的外部能力接口；外部实现实现这些接口。具体实例在入口的组装代码中传入。业务代码可接收存储、环境恢复或观测能力，但不导入其具体实现。

接口定义放在使用该能力的功能模块附近，只为真实需要定义；不建立庞大的统一接口目录。数据定义不依赖其他四部分。禁止循环导入、全局可变上下文和把所有业务堆入一个 services.py。

功能模块之间需要协作时，优先由 workflows 组织；确有直接依赖时明确记录且保持单向。纯规则函数仅依赖输入数据。错误使用明确类型，不能用通用异常把环境阻断、场景无效和证据不足混成一个状态。

## 4. 项目结构

```text
project-doctor/
├── pyproject.toml
├── src/project_doctor/
│   ├── entrypoints/             # MCP 入口及实例组装
│   ├── workflows/               # 创建任务、实验执行、恢复与收尾
│   ├── features/
│   │   ├── environments/        # 环境准备、指纹和恢复规则
│   │   ├── scenarios/           # 场景发现、准备、断言与复用
│   │   ├── experiments/         # 实验约束、基线、干预与比较
│   │   ├── diagnosis/           # 三类问题的证据门槛和规则
│   │   └── reports/             # 影响排序、诊断卡与报告
│   ├── integrations/
│   │   ├── mysql/               # 数据访问、事务、迁移
│   │   ├── docker/              # Compose 和生命周期操作
│   │   ├── http/                # 请求执行、负载工具接入
│   │   ├── observation/         # SQL、trace、计划、调用位置转换
│   │   └── artifacts/           # 原始证据文件保存与读取
│   └── models/                  # 统一业务数据、引用与错误类型
├── agh/                         # 配置、诊断指令、固定版本记录
├── tests/
├── demo/                        # 保留现有教学示例
└── docs/
```

目录是职责导航，不要求每个目录复制 controller/service/repository 多层模板。不为一行逻辑创建空壳类。文件和函数按具体动作命名，使用清晰参数和返回类型；注释解释原因和限制。

## 5. 业务执行与状态归属

一次实验的流程：

1. AGH 中的模型提出实验，并经 MCP 调用已声明工具。
2. 入口校验输入，业务流程核对任务状态、预算和环境可用性。
3. 实验模块核对基线、变化因素、数据条件和预期业务结果。
4. 外部实现执行受限请求、采集观测并保存原始证据。
5. 业务流程安排恢复并验证恢复结果；恢复失败则隔离环境。
6. 诊断模块检查证据、实验可比性和竞争解释；不满足时返回待验证线索。
7. 持久化结果，返回结果摘要和证据引用；AGH 决定下一项动作。

业务工具拆分应让 AGH 可观察到场景、实验和证据检查等动作，不能把整个诊断循环封装成一个黑盒工具。

AGH 保存会话与调用记录，MySQL 保存可恢复的业务事实。通过 task_id、experiment_id、AGH session_id 和可获得的工具调用 ID 关联；缺少某项 AGH 标识时明确记录，不能伪造。日志和模型文字不是环境恢复成功的依据。

MySQL 记录任务运行状态、实验阶段和环境健康状态，三者分别管理，避免混为一个状态字段。实验至少区分已准备、执行中、恢复中、已结束和需核对；环境至少区分可用、恢复中和已隔离。中断后先核对持久记录、实际环境和制品，再决定恢复、继续或终止；不直接重放所有调用。

每个工具声明超时、预算、副作用和可重放条件。相同请求重复到达时使用业务操作标识核对已有结果；执行状态不明确时先核对，不能把可能有副作用的操作自动再执行一次。

首版支持单机运行，每个隔离环境串行执行实验。独占约束必须覆盖整个实验和恢复过程，不能仅锁住单次 HTTP 请求。

## 6. MySQL 与证据制品

| 数据 | 保存方式 |
| --- | --- |
| 任务及状态、预算、执行阶段 | MySQL，支持事务更新和状态核对 |
| 场景与数据配置 | MySQL，保存版本、来源和复用条件 |
| 实验、假设、观测摘要、结论 | MySQL，关联代码、环境和快照标识 |
| 证据索引 | MySQL，保存制品 ID、相对位置、格式版本和内容校验值 |
| 原始 trace、SQL 记录、计划与日志 | 独立文件目录，保留原始内容 |

MySQL 写入不等于文件写入成功。制品先写入临时文件并完成校验，再发布文件及索引；只有文件可读取且索引有效时，证据才可用于正式结论。中断产生的未引用文件可核对清理；索引指向缺失文件时标记证据不可用，不静默生成报告。

文件位置相对于配置的制品根目录记录，避免把机器绝对路径绑定进报告。运行目录与目标仓库分离，不提交 Git。密钥只保存凭据引用，不写入场景、报告或原始日志；采集阶段需过滤敏感信息。

历史场景可复用，历史测量不能自动代表当前性能。每次观测关联提交、环境配置、数据快照和观测配置；变更后重新测量。

## 7. 变更与验证方式

| 后续修改 | 主要修改位置 | 应验证的边界 |
| --- | --- | --- |
| 调整 N+1 判定 | features/diagnosis | 证据齐全可判定；缺少调用位置不能变为正式结论 |
| 替换观测工具 | integrations/observation | 新输出符合相同数据合同，证据引用仍可读取 |
| 修改实验顺序 | workflows | 预算、恢复与状态约束仍成立 |
| 调整 MySQL 实现 | integrations/mysql | 事务、重复调用及中断核对行为一致 |
| 调整报告展示 | features/reports | 不改变判定结果，不重复计算影响 |
| 更换模型 | agh 配置 | 核心业务规则不改；重新验证实际工具选择与调用 |

开发按完整业务链路交付：先让一个真实场景走完准备、测量、比较、恢复、校验和报告，再扩展其余问题。先定义该链路需要的数据合同，不一次性设计所有未来能力。

验收至少覆盖：正常实验；业务请求无效；证据或调用位置缺失；实验条件不可比；工具中断与重复调用；恢复失败；证据文件缺失。规则测试不依赖真实模型；外部适配器做集成验证；AGH 链路单独验证真实工具记录。

## 8. 当前验证边界与下一步

2026-10-02 实施补充：已实现公共模型及 B 侧显式场景 manifest、慢查询证据门槛、报告与 MCP 入口。用户批准 ExperimentResult 兼容增加可选 spec，用于保留实际实验配置，缺失时降级线索；三个共享能力接口不变。官方 SDK 协议和 scripted B 流程通过不能替代真实 AGH／MySQL／目标环境验收，实际边界见 [B 接入记录](../../development/b/compatibility.md)。

已确认：Python + MCP + AGH、MySQL，以及职责清晰、低耦合、人可读的组织原则。

未验证：真实诊断模型经 MCP 调用 Python 业务工具、结构化结果在所选 AGH 版本中的呈现、MySQL 持久化与中断核对、真实目标环境恢复，以及完整 SQL 到代码位置证据链。现有 demo 使用模拟数据，不代表这些能力已完成。

本文复核后再制定分阶段实现计划。首阶段优先验证 AGH → MCP → Python → MySQL → AGH 的最小调用链，保存实际记录；该检查不替代后续真实实验与恢复验收。
