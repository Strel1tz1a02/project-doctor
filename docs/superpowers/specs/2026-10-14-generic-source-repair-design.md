# 通用源码修复与诊断复测设计

日期：2026-10-14。用户已确认：修复层负责判断和提出改法；平台隔离执行；诊断层独立验证结果。

## 目标与边界

修复工作流消费持久化的 `Finding`、证据、场景和目标提交。修复 Agent 可对受控应用源码提出统一 diff；平台负责源码身份、补丁范围、隔离构建、持久状态与恢复。修复工作流不推断性能收益。诊断层通过统一的原版/补丁版入口采集和判断，并保留问题类型专属的机制证据。

“通用”指修复决策、源码上下文、补丁执行和状态机不再依赖 N+1 或 MyBatis 的语义。它不意味着任意问题都能获得 `retested`：诊断层没有相应的复测判据时，明确拒绝验证，不回填收益。

首版目标仍为 Java 项目的三类已定义性能问题，允许修改已提交的 `src/main` 下 Java/XML 应用源码。已有 N+1 `batch_in` 判据和真实 Docker 路径继续有效。慢查询要求目标 SQL 的扫描量、SQL 耗时及请求耗时均有可区分改善；深分页仅支持 keyset 方案，要求复现原 OFFSET、补丁使用游标且去掉 OFFSET，并证明业务结果及工作量改善。其他方案没有诊断判据时拒绝 `retested`。

## 交接与修复决策

诊断侧交接至少包括：`Finding` 的问题类型、状态、代码位置、实验和证据引用、`Recommendation`、场景 ID 及目标提交。修复入口只接受 `lead|verified` 且引用均在持久任务中的结论；必须核验制品和源码提交。`refuted|unclassified`、缺证据、目标位置不一致时不改代码。修复 Agent 可以选择不提交补丁；该决定不伪造 `RepairRecord`。

`inspect_fix_target` 返回每个有证据的源码位置的行号、上下文和文件 SHA-256，以及允许改动的应用源码范围；`read_fix_source` 可以按行读取该范围内的源码。已有 N+1 mapper/caller 细节作为额外提示，不作为通用合同的必填项。

`submit_fix_patch` 对所有受支持类型执行同一流程：校验统一 diff、路径包含关系、文件身份与大小，禁止仓库外路径、符号链接、二进制、重命名、删除、测试/评估/诊断配置改动；在隔离副本应用；构建原版和补丁版不同镜像；记录补丁、前后哈希和镜像摘要。N+1 可保留更严格的语义预检，但其他类型不得通过 N+1 正则判定。

## 诊断层统一版本对照入口

`DiagnosisRetestService.run(bundle, finding, repair)` 是唯一成功判定入口。共性硬门槛：补丁和构建制品可核验、镜像身份不同、两次独立任务、同场景/数据快照/缓存/负载、业务结果和恢复均有效。具体问题的 SQL 机制、收益显著性由诊断层按 `Finding.kind` 选择验证器。未注册或证据不足时返回带原因的拒绝，保留已核验样本，不把 `Recommendation` 改为 `retested`。

修复层沿用当前 MySQL `RepairRecord`、进程租约、异步 `verify_fix`、`get_fix_status`、未知状态核对和环境清理。只在诊断层返回通过时原子回填 Recommendation 的三个复测字段。

## 验收

规则测试覆盖诊断到修复交接、拒绝无证据结论、合法 Java/XML 源码补丁、越界补丁、N+1 专用校验不污染通用路径、无验证器时不得声称成功、错误业务结果/噪声/丢失制品不得回填。已有 N+1 Docker/MySQL 链需保持通过。慢查询和 keyset 深分页已实现诊断判据，但真实原版/补丁版 Docker 验收尚未完成；在此之前仅能称代码路径与规则测试通过，不能称新增类型的真实效果已验收。
