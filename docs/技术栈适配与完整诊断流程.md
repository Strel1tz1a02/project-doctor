# 技术栈适配与完整诊断流程（语言 → ORM → 数据库）

日期：2026-10-01
状态：技术设计稿，承接 [`2026-09-30-backend-performance-diagnosis-agent-design.md`](superpowers/specs/2026-09-30-backend-performance-diagnosis-agent-design.md) 的系统级设计，落地「跨语言/ORM/数据库如何统一、如何针对性调用工具」。

---

## 0. 阅读方式

本文回答一件事：**诊断 Agent 面对一个陌生后端项目时，从识别语言/ORM/数据库，到采集证据、定位根因、给出建议、复测收益的完整链路怎么走，每一步调什么工具，哪些跨栈统一、哪些按栈适配。**

全文用一个分层模型贯穿：**在「SQL + 遥测」这一层统一，在「采集 / 定位 / 修复建议」三件事上适配**。理由见第 1 节。

约定：文中 `[统一]` 表示跨栈写一次、全栈复用；`[适配: 栈]` 表示该栈各写一套适配器；`[DB 特定]` 表示按数据库写。

---

## 1. 分层总原则：统一与适配的边界

数据库只认 SQL，不管上层是 SQLAlchemy 还是 Hibernate——**ORM 吐出来的 SQL 是全栈统一的公约数**。因此：

| 层 | 是否统一 | 内容 |
|---|---|---|
| 证据契约层 | ✅ `[统一]` | `Scenario/Observation/Hypothesis/Finding` 等结构化格式 |
| SQL 规范层 | ✅ `[统一]` | SQL 归一化（参数模板化）、执行计划解析 |
| 遥测语义层 | ✅ `[统一]` | OpenTelemetry DB span 字段（`db.query.text` 等） |
| 问题判据层 | ✅ `[统一]` | 慢查询/N+1/深分页的判据是 DB 层现象，与语言无关 |
| 诊断闭环层 | ✅ `[统一]` | 假设 → 实验 → 证据 → 复测 的 6 步循环 |
| **采集** | ❌ `[适配]` | 怎么让 ORM 把 SQL 交出来（各栈开关不同） |
| **定位** | ❌ `[适配]` | 怎么把 SQL 指回代码行（ORM 生成 SQL，源码无原文） |
| **修复建议** | ❌ `[适配]` | `selectinload` vs `JOIN FETCH` vs 批量 `IN`（栈级方言） |
| 数据库执行计划/统计 | ⚠️ `[DB 特定]` | 接口统一，实现按 DB |

**核心原则（来自正式设计稿，必须遵守）：**
1. 统一的是**证据格式**，不是 ORM 接口——不要试图让所有 ORM 变成一个接口。
2. 核心流程**禁止散落 `if 是 Hibernate` 之类的条件分支**，差异只能关在适配器内部。
3. **先做第一个栈的适配器，再用第二个栈验证通用协议**，按真实差异抽象，禁止预建庞大插件框架。
4. 首版只承诺 3 类问题（慢查询/全表扫描、N+1、深分页），其余保留为「未分类异常」。

## 2. 主流覆盖矩阵

按「语言 × ORM × 数据库」三元组划分。**Tier 1 是首版必须适配的主流组合，Tier 2 是后续扩展。**

### Tier 1（首版主流）

| 语言 | ORM / 数据访问层 | 数据库 | 采集工具（现有可调用） |
|---|---|---|---|
| Java | Spring Data JPA / Hibernate | MySQL / PostgreSQL | `opentelemetry-javaagent`、Hibernate SQL 日志、[datasource-proxy](https://github.com/tttdyy/datasource-proxy)、[p6spy](https://github.com/p6spy/p6spy) |
| Java | MyBatis | MySQL / PostgreSQL | `opentelemetry-javaagent`、MyBatis 日志、datasource-proxy |
| Python | SQLAlchemy | MySQL / PostgreSQL | [opentelemetry-instrumentation-sqlalchemy](https://opentelemetry-python-kinvolk.readthedocs.io/en/latest/instrumentation/sqlalchemy/sqlalchemy.html)、`echo=True`、[nplusone](https://github.com/jmcarp/nplusone) |
| Python | Django ORM | MySQL / PostgreSQL | `opentelemetry-instrumentation-django`、[django-silk](https://github.com/jazzband/django-silk)、[django-querycount](https://github.com/bradmontgomery/django-querycount)、nplusone |
| Go | GORM | MySQL / PostgreSQL | [otelsql](https://github.com/XSAM/otelsql)、GORM `DryRun`/logger |
| Node.js | Sequelize / Prisma | MySQL / PostgreSQL | `@opentelemetry/instrumentation-pg` / `-mysql` / `-sequelize`、Prisma 查询事件 |
| Ruby | ActiveRecord | MySQL / PostgreSQL | `opentelemetry-instrumentation-active_record`（**需另加 `active_support` 订阅 `sql.active_record` 才拿到 SQL 文本**）、[bullet](https://github.com/flyerhzm/bullet)、[marginalia](https://github.com/37signals/marginalia) |
| C# | Entity Framework Core | SQL Server / PostgreSQL | `OpenTelemetry.Instrumentation.EntityFrameworkCore`（**beta 包，需 `SetDbStatementForText=true` 才输出 SQL**） |
| PHP | Eloquent（Laravel） | MySQL / PostgreSQL | `open-telemetry/opentelemetry-auto-laravel`、Laravel query log |

### Tier 2（后续扩展）

Node + TypeORM、Go + sqlx/ent、Java + jOOQ、Python + peewee 等——在 Tier 1 跑通后按「真实差异」逐个接入，不预建。

### 数据库侧（`[DB 特定]`，接口统一）

| 数据库 | 慢查询采集 | 执行计划 | 统计/计数器 |
|---|---|---|---|
| MySQL | slow query log | `EXPLAIN` / `EXPLAIN ANALYZE`(8.0.18+) | `performance_schema`：`Handler_read_rnd_next`、`Select_scan`、`Slow_queries` |
| PostgreSQL | `log_min_duration_statement` + `auto_explain` | `EXPLAIN (ANALYZE, BUFFERS)` | `pg_stat_statements`、`pg_stat_user_tables`（`seq_scan`/`idx_scan`） |
| SQL Server | Query Store / 扩展事件 | `SET STATISTICS` / 实际执行计划 | `sys.dm_exec_query_stats` |
| Oracle | AWR / `V$SQL` | `EXPLAIN PLAN` | `V$SQLAREA` |

## 3. 统一层（写一次，全栈复用）

### 3.1 统一证据契约 `[统一]`

核心模型使用带版本的结构化契约（字段含义与单位在唯一位置定义，报告不直接读工具私有输出）：

```
Scenario        场景：操作路径 + 请求序列 + 参数来源 + 断言 + 数据规模 + 并发 + 来源(用户/文档/推断)
DatasetProfile  数据画像：规模、分布、关联基数、热点/长尾、是否合成
ExperimentSpec  实验规格：唯一变量 + 预算 + 缓存/预热状态
Observation     观测：原始测量（SQL 文本、耗时、扫描行数、trace_id、代码位置、执行计划）
Hypothesis      假设：可观测预测 + 反证条件 + 状态(候选/支持/被否)
Finding         结论：受影响接口 + 触发条件 + 证据索引 + 影响数据 + 建议 + 适用范围
```

### 3.2 统一 SQL 规范化 `[统一]`

所有采集到的 SQL，先做**归一化**再进下游：

- **模板化（参数化）**：把字面量替换为 `?`，得到 SQL 模板（如 `SELECT * FROM users WHERE id = ?`）。
  - 用途：N+1 的「同构 SQL 指纹」检测（同模板、仅参数不同）。
- **保留原文**：原始 SQL 文本与参数单独保存，用于 `EXPLAIN` 复现。
- **规范化**：去除 ORM 自动别名差异（`owner0_` 等），统一大小写与空白，便于跨栈比较。

> 慢查询判据（`Rows_examined/Rows_sent`）、深分页判据（大 `OFFSET`）都在归一化后的 SQL 与统计上做，与语言无关。

### 3.3 统一遥测语义 `[统一]` —— OpenTelemetry

以 OTel DB span 语义作为跨栈统一遥测格式：

| 字段（2026 稳定方向） | 旧名（仍兼容输出） | 含义 |
|---|---|---|
| `db.query.text` | `db.statement` | SQL 文本（采集时需脱敏） |
| `db.system.name` | `db.system` | 数据库类型（postgresql/mysql…） |
| `db.operation.name` | `db.operation` | 操作类型 |
| `db.collection.name` | `db.sql.table` | 表名 |
| `db.namespace` | `db.name` | 库名 |

配套：`trace_id`/`span_id`、span 耗时、`code.stacktrace`（定位用）。
迁移控制：`OTEL_SEMCONV_STABILITY_OPT_IN=database`（旧属性默认兼容至少 6 个月）。

> 采集工具统一输出这套字段 → 适配器只需把各栈原生 span 映射成统一 `Observation`，无需每个语言各写 SQL 采集器。

### 3.4 统一问题判据 `[统一]`（DB 层现象，与语言无关）

| 问题 | 判据（提示性 → 决定性） | 详见 |
|---|---|---|
| 慢查询 / 全表扫描 | `Rows_examined ≫ Rows_sent`（提示）→ `EXPLAIN type=ALL / key=NULL`（访问路径） | [deepdive-01](diagnosis/performance-agent-deepdive-01-slow-query.md) |
| N+1 查询 | 同构小查询数量爆炸 + 查询次数随父对象数线性增长 + 定位到循环/懒加载代码 | [deepdive-02](diagnosis/performance-agent-deepdive-02-n-plus-one.md) |
| 深分页 | SQL 含大 `OFFSET` + `Rows_examined ≈ M+N` + 耗时随页码线性上升 | [deepdive-04](diagnosis/performance-agent-deepdive-04-deep-pagination.md) |

关键：判据只触发**怀疑**，不能单独充当根因结论；结论必须来自对照实验 + 代码/执行计划证据。

### 3.5 统一诊断闭环 `[统一]`

无论什么栈，主循环都是这 6 步（详细见第 6 节的 9 步落地版）：

```
限定任务 → 建立基线 → 提出≤3个竞争假设 → 选择能排除至少一个假设的实验 → 定位与建议 → 独立复测（失败送回再诊断）
```

## 4. 适配层（每栈三件，唯一需要按栈写的部分）

### 4.1 采集适配器 `[适配: 栈]` —— 怎么让 ORM 交出 SQL

每个栈一套「采集接入配方」，统一走 OTel 语义。核心选择：**优先 ORM/驱动层埋点，兜底用驱动代理或 eBPF**。

| 层次 | 方式 | 适用 |
|---|---|---|
| ORM 层 | OTel instrumentor（sqlalchemy / django / efcore / sequelize…） | 主流 ORM，最推荐 |
| ORM 层 | ORM 自带日志/事件（SQLAlchemy `echo`、GORM logger、Eloquent query log） | 无 OTel 时的轻量替代 |
| 驱动层 | JDBC 代理（datasource-proxy / p6spy）、otelsql | 绕过 ORM，直接抓 JDBC/`database/sql` |
| 内核层 | eBPF（Pixie / Coroot / Beyla） | 免改代码、语言无关；**仅 Linux/K8s，Windows 本机不可用** |

> 注意：不要同时开自定义事件钩子 + OTel 埋点，会重复记录；设置采样率防止 span 爆炸。

### 4.2 定位适配器 `[适配: 栈]` —— 怎么把 SQL 指回代码

ORM 生成的 SQL 在源码里没有原文（自动别名、懒加载、query builder），定位是**最需要自研的一环**。可复用的现有件：

| 方式 | 工具 | 覆盖 |
|---|---|---|
| SQL 注释注入 | [opentelemetry-sqlcommenter](https://open-telemetry.github.io/opentelemetry-sqlcommenter/faq/)、[marginalia](https://github.com/37signals/marginalia) | Hibernate/Spring、SQLAlchemy/Flask、Django、Sequelize/Knex、ActiveRecord |
| ORM 事件钩子抓调用栈 | SQLAlchemy `before_cursor_execute` + `traceback` | SQLAlchemy 等 |
| OTel 属性 | `code.stacktrace` / `code.function` | 多数 OTel 埋点 |
| 静态分析（后续） | [SLocator](http://petertsehsun.github.io/papers/SLocator_Paper.pdf)、[SQLens](https://dl.acm.org/doi/pdf/10.1145/3788853.3803091) | 离线 code↔SQL 索引 |

首版策略：**运行时定位**（sqlcommenter + 事件钩子）为主；静态分析作为后续增强。

### 4.3 修复模板适配器 `[适配: 栈]` —— 栈级方言

同一问题的修复概念通用，但**写法是栈级方言**。模板库按「问题 × 栈」组织：

| 问题 | 通用概念 | 各栈写法示例 |
|---|---|---|
| N+1 | 批量预取关联 | SQLAlchemy `selectinload`/`joinedload`；Hibernate `JOIN FETCH`/`@BatchSize`；Django `select_related`/`prefetch_related`；GORM `Preload`；ActiveRecord `includes`；EF Core `Include`；Eloquent `with` |
| 慢查询 | 建索引 / 改写谓词为范围条件 | `DATE(col) = ?` → `col >= ? AND col < ?`（各 DB 语法近同） |
| 深分页 | keyset（游标）分页 | 通用 `WHERE id > :last_id ORDER BY id LIMIT n` |

> 每个建议都标注「适用条件 + 代价」，未经复测只能写「预计作用机制」，不能写「已提升 X%」。

## 5. 数据库适配 `[DB 特定]`

执行计划与统计的**接口统一**（都是「给一条 SQL → 返回扫描行数/访问路径/耗时」），实现按 DB 写：

```
统一接口：
  get_plan(sql)   -> { access_type, key, estimated_rows, actual_rows, cost }
  get_stats(sql)  -> { rows_examined, rows_sent, mean_exec_time, calls }
  get_counters()  -> { seq_scan_count, slow_query_count, ... }

实现：MySQL(EXPLAIN/slow log/performance_schema) / PG(pg_stat_statements/auto_explain) / ...
```

首版只实现 MySQL 与 PostgreSQL 两个 `[DB 特定]` 适配器，其余按需追加。

## 6. 完整诊断流程（9 步落地版）

每步标注「统一 / 适配」，给出输入、调用工具、输出。

### Step 0 项目预检与栈识别 `[适配: 栈]`

- **输入**：项目仓库路径 + 本地/测试地址。
- **动作**：识别构建文件与依赖，判定「语言 + ORM/数据访问层 + 数据库」三元组（如 `requirements.txt` 有 `sqlalchemy` + `pymysql` → Python/SQLAlchemy/MySQL）。
- **输出**：栈指纹 `StackFingerprint`，据此选择后续所有适配器。

### Step 1 隔离环境准备 `[统一]`

- **动作**：复用仓库已有的容器/迁移/种子配置，必要时生成隔离运行配方；记录环境指纹（OS/依赖版本/DB 版本）。
- **输出**：可重复启动/重置的隔离副本 + `EnvironmentFingerprint`。

### Step 2 采集接入 `[适配: 栈]`

- **动作**：按第 4.1 节为当前栈注入采集工具（OTel instrumentor / JDBC 代理 / ORM 日志），确认能抓到带 `trace_id` 的 SQL span。
- **输出**：可用的观测通道，统一映射为 `Observation`。

### Step 3 场景发现 `[统一]`

- **动作**：从路由/OpenAPI/现有测试枚举可访问操作，做有上限的轻量请求，记录接口、状态、响应与 SQL 活动；写入操作只在隔离副本执行，轮次间可重置。
- **输出**：候选 `Scenario` 列表（含断言、参数来源、数据规模）。

### Step 4 建立基线 `[统一]`

- **动作**：固定数据/负载/缓存/预热，用 [k6](https://grafana.com/docs/k6/latest/using-k6/scenarios/) 重复测量延迟分布、错误率、资源指标；波动过大则先调实验，不急于归因。
- **输出**：基线指标（p95/吞吐/错误率/CPU）+ 测量波动记录。

### Step 5 提出竞争假设 `[统一]`

- **动作**：诊断模型结合代码、指标、trace 给出 ≤3 个候选瓶颈，每个写明**可观测预测**（如「若是 N+1，则单请求同构 SQL 数应随父对象数线性增长」）。
- **输出**：`Hypothesis[]`。

### Step 6 受控实验 `[统一]` + 采集 `[适配]` + 计划 `[DB 特定]`

- **动作**：选择能排除至少一个假设的实验（改数据规模/并发/缓存，或采 profile / `EXPLAIN`）；实验后恢复环境。
- **调用**：负载 k6；采集走 Step 2 适配器；执行计划走第 5 节 DB 适配器（`get_plan` / `get_stats`）。
- **输出**：`Observation[]` + `ExperimentSpec` + 被否定的假设记录。

### Step 7 定位与建议 `[统一]` + 定位/修复 `[适配: 栈]`

- **动作**：把实验结果指向具体函数/查询/调用链；SQL→代码走第 4.2 节，修复建议走第 4.3 节模板库。
- **输出**：`Finding`（含 SQL、文件:行号、证据索引、建议、适用范围）。

### Step 8 独立复测 `[统一]`

- **动作**：预先固定的**独立验证器**重跑正确性测试 + 基准负载；修复方不能改验证器/测试数据/通过标准。未达标或结果错误 → 判失败，反证送回 Step 5。
- **输出**：前后对照结果（延迟/扫描行数/查询次数/正确性）。

### Step 9 报告与归档 `[统一]`

- **动作**：按本次测试负载下证据支持的影响排序；输出报告首页（环境版本、适用性摘要、覆盖范围、已验证问题、未验证线索、未分类异常）+ 每张诊断卡 + 执行记录。
- **输出**：可复现诊断报告 + 场景/证据归档（供下次复用与去重）。

> 失败与继续执行（环境阻断、证据不足、测量波动大、工具中断等）按正式设计稿 §7 处理，不统一称为「重试」。

## 7. 三类问题的诊断流程（首版范围）

### 7.1 慢查询 / 全表扫描

```
① 现象：接口 p99 上升、DB CPU/IO 升高、Slow_queries 斜率陡增        [统一]
② 收敛：慢日志/统计里取耗时最长、Rows_examined 最大的 SQL           [DB 特定]
③ 确认：Rows_examined ≫ Rows_sent？                                 [统一]
④ 计划：EXPLAIN 看 type=ALL / key=NULL                             [DB 特定]
⑤ 定位：SQL → 触发代码位置                                          [适配]
⑥ 建议：建索引 / 改写谓词为范围条件，复测收益与代价                  [统一+适配]
```

### 7.2 N+1 查询

```
① 现象：接口 p99 上升，但慢查询日志没有明显慢 SQL                    [统一]
② 提示：按 SQL 模板聚合，同一请求内大量同构小查询                    [统一]
③ 证明：查询参数来自主查询结果集合，次数随父对象数线性增长           [统一]
④ 定位：循环内访问关联属性 / 循环内 query 的代码位置                  [适配]
⑤ 建议：批量预取（selectinload / JOIN FETCH / includes / Preload …）  [适配]
⑥ 复测：单请求查询次数 N+1 → 1~2                                    [统一]
```

### 7.3 深分页

```
① 现象：分页接口「翻到后面变慢」                                     [统一]
② 识别：慢 SQL 带大 OFFSET                                          [统一]
③ 对照：固定筛选/排序/页大小/数据，改 OFFSET 比耗时与处理行数        [统一]
④ 归因：EXPLAIN 区分 OFFSET 代价 vs 全表扫描代价（可共存，先修全表扫）[DB 特定]
⑤ 建议：keyset 分页 / 限制最大页                                     [统一+适配]
⑥ 复测：深页耗时大幅下降                                            [统一]
```

## 8. 工具调用清单（附录）

| 工具 | 类别 | 覆盖 | 用途 | 调用形式 |
|---|---|---|---|---|
| OpenTelemetry SDK + instrumentors | 采集 | 全语言 | 统一 SQL span（`db.query.text`） | 库 / `-javaagent` |
| opentelemetry-sqlcommenter / marginalia | 定位 | Hibernate/Spring、SQLAlchemy/Flask、Django、Sequelize/Knex、ActiveRecord | SQL→代码来源注释 | 库 |
| [nplusone](https://pypi.org/project/nplusone/)（新重写 [nplus1](https://pypi.org/project/nplus1/)）/ [bullet](https://github.com/flyerhzm/bullet) / django-querycount | N+1 检测 | Python、Ruby | 现成 N+1 检测，可作基线对照；**仅开发环境** | 库 |
| datasource-proxy / p6spy / otelsql | 采集 | Java / Go | 驱动层 SQL 代理 | 库 / 代理 |
| pg_stat_statements / auto_explain | 统计+计划 | PostgreSQL | 均值耗时、行数、执行计划 | SQL / 视图 |
| slow query log / performance_schema | 采集+统计 | MySQL | Rows_examined、计数器 | 日志 / SQL |
| k6 | 负载 | 无关 | 基线 + 复测负载 | CLI |
| async-profiler / py-spy / pprof | profiler | JVM / Python / Go | CPU/阻塞归因（按需） | CLI |
| Pixie / Coroot（eBPF） | 采集 | 语言无关 | 免埋点 SQL 抓取；**仅 Linux/K8s** | DaemonSet |
| SLocator / SQLens | 定位（后续） | 研究 | 静态 code↔SQL 索引 | 离线 |

> **验证结论（2026-10-01 核实）**：上表工具均可调用。要点——C# 的 EF Core 埋点是 beta 包（API 可能变动）；Ruby 的 active_record 埋点默认只出 ORM 层 span，需另订阅 `sql.active_record` 才拿到 SQL 文本；`nplusone` 已有 Python 3.11+/SQLAlchemy 2.0 的 `nplus1` 重写，且仅限开发环境使用。

## 9. 如何把这些能力做成 Agent 可调用的工具 `[工具化]`

本节回答：第 2～8 节那些「现有技术」怎么包装成 Agent 能调用、能记录、能约束的工具。

### 9.1 工具的本质：声明式接口 + 确定性执行

给 Agent 调用的「工具」，本质是一个带完整契约的普通函数：

```
Tool = {
  name:          "get_plan",
  description:   "对一条 SQL 获取执行计划（访问路径/扫描行数/代价），用于慢查询/深分页判据",
  input_schema:  { sql: string, database: "mysql"|"postgresql" },
  output_schema: { access_type, key, estimated_rows, actual_rows, cost },
  side_effect:   false,        // 只读
  budget:        { timeout_ms: 5000, max_calls: 50 },
  replayable:    true,         // 同输入可安全重放
}
```

关键分界：**工具本身是确定性的普通程序**（采集、测量、计划、快照、证据校验）；**模型只负责两件事——决定调用哪个工具、解读返回的结构化结果**。副作用、预算、授权由 harness（AGH）强制，不由模型文字决定。

### 9.2 暴露机制：MCP / AGH 插件 / 原生 tool-use（同一套定义，三种出口）

同一套工具定义，用三种机制都能暴露，无需改工具实现：

| 机制 | 说明 | 适用 |
|---|---|---|
| MCP（Model Context Protocol） | 标准工具暴露协议，JSON Schema 描述输入输出 | 跨框架通用，首选 |
| AGH 插件 | 设计稿引用的 AGH 后端工具注册入口（`backend.zh-CN.md`） | 赛事要求 AGH 承担执行链路 |
| 框架原生 tool-use | OpenAI/Claude/AGH 原生 function calling | 单框架最省事 |

无论哪种，Agent 看到的都是「工具名 + 描述 + JSON Schema」，调用时传参、拿结构化结果，三种出口可互换。

### 9.3 核心决策：暴露「统一工具面」，而不是 30 个原始工具

**不要**把 SQLAlchemy 埋点、datasource-proxy、pg_stat_statements、EXPLAIN 这些原始工具直接堆给模型——那样模型要理解每个栈的差异，核心流程里就会出现「if 是 Hibernate」的分支，违反设计稿约束。

**要**：把「统一契约 + 适配器」贯彻到工具层——Agent 只看到**一套小而有边界的统一工具**（一个诊断能力一个工具，约 12 个），适配器根据 `StackFingerprint` 在底下选对实现：

```
Agent 可见的统一工具面（与语言无关）            底下的适配器（模型不可见）
──────────────────────────────────          ─────────────────────────────
preflight()            → 栈识别与可启动性     读依赖/构建文件 → StackFingerprint
prepare_env/reset()    → 隔离环境准备/恢复    Docker / 脚本快照
discover_scenarios()   → 场景发现            路由/OpenAPI/测试枚举
run_scenario()         → 执行单个场景        HTTP 客户端 + 断言
collect_observations() → 统一证据采集        OTel instrumentor / JDBC代理 / ORM日志
get_plan(sql)          → 执行计划            MySQL EXPLAIN / PG auto_explain
get_sql_stats(sql)     → 查询统计            slow log / pg_stat_statements
locate_origin(sql)     → SQL→代码位置        sqlcommenter / 事件钩子 / 静态分析
run_baseline()         → 建立基线            k6 场景 + 阈值
run_experiment()       → 受控实验            k6 + 采集 + 计划（唯一变量）
suggest_fix(finding)   → 修复建议            模板库（按栈方言）
verify(finding)        → 独立复测            正确性测试 + k6 前后对照
```

这样模型面对的是**与语言无关的诊断动作**，栈差异全部封装在适配器里。

### 9.4 工具元数据契约（每条必填）

| 字段 | 含义 | 取值示例 |
|---|---|---|
| `side_effect` | 只读 / 有副作用 | `get_plan`=false；`reset_env`=true |
| `budget` | 超时 + 调用上限 | `{timeout_ms, max_calls}` |
| `replayable` | 同输入可否安全重放 | 只读=true；写操作需快照后=true |
| `evidence` | 是否产出结构化证据 | `collect_observations`=true |
| `stack_required` | 是否依赖先 `preflight` | 采集/定位/修复=true |

副作用工具必须满足：隔离副本内执行 + 预算硬限制 + 可检查点恢复；模型无法绕过这些约束（由 harness 强制）。

### 9.5 完整工具定义示例

**只读工具 `get_plan`：**

```json
{
  "name": "get_plan",
  "description": "对一条 SQL 获取执行计划，返回访问路径、索引、估算与实际行数，用于慢查询/深分页判据。",
  "input_schema": {
    "type": "object",
    "properties": {
      "sql": { "type": "string", "description": "归一化后的原始 SQL" },
      "database": { "type": "string", "enum": ["mysql", "postgresql"] }
    },
    "required": ["sql", "database"]
  },
  "output_schema": {
    "type": "object",
    "properties": {
      "access_type": { "type": "string" },
      "key": { "type": ["string", "null"] },
      "estimated_rows": { "type": "integer" },
      "actual_rows": { "type": "integer" },
      "cost": { "type": "number" }
    }
  },
  "side_effect": false,
  "budget": { "timeout_ms": 5000, "max_calls": 50 },
  "replayable": true,
  "evidence": true
}
```

**副作用工具 `run_experiment`：**

```json
{
  "name": "run_experiment",
  "description": "在隔离副本上按 ExperimentSpec 执行受控实验（唯一变量 + 预算），返回观测结果。",
  "input_schema": {
    "type": "object",
    "properties": {
      "experiment_spec": { "$ref": "ExperimentSpec" },
      "variables": { "type": "object" }
    },
    "required": ["experiment_spec"]
  },
  "side_effect": true,
  "budget": { "timeout_ms": 120000, "max_calls": 20 },
  "replayable": true,
  "precondition": "env_is_snapshot_restored",
  "evidence": true
}
```

### 9.6 调用闭环与执行记录

```
诊断模型 → 选工具 + 传参（结构化）
   ↓
AGH/harness → 校验权限/预算/副作用 → 执行适配器 → 记录本次调用
   ↓
工具返回 → 结构化 Observation（非自由文本）
   ↓
诊断模型 → 更新假设账本 → 选下一个工具
```

每一步「模型决策 + 工具调用 + 返回结果」都被 AGH 记录，形成赛事要求的**可核查执行记录**；纯数据转换与排序不经过模型、不依赖 AGH 会话对象（设计稿 §3 约束）。

### 9.7 工具分级与模型边界

| 层 | 谁负责 | 内容 |
|---|---|---|
| 决策层 | 诊断模型 | 写假设、选实验、解读证据、写定位叙述 |
| 执行层 | 确定性工具 | 采集、测量、计划、快照、证据校验 |
| 约束层 | harness/AGH | 预算、副作用授权、记录、失败恢复 |

模型能改的是「假设与解释」，改不了「验证器、测试数据、通过标准、工具副作用」——这保证「独立验收」不被修复方污染（对齐闭环第 6 步）。

## 10. 实施顺序建议

1. **先定样例栈**（建议 Python + SQLAlchemy + PostgreSQL 或 MySQL），实现该栈的三件适配器（采集/定位/修复）+ MySQL/PG 两个 DB 适配器。
2. **跑通 6 步闭环**，用 `nplusone` 等现成检测器做结论对照，验证「假设-实验-证据」编排正确。
3. **加第二个栈**（如 Java + Hibernate），按真实差异抽象适配器接口；抽象不出来就回头改契约。
4. **补对照案例**（一个会误导直觉的场景），证明 Agent 通过实验排除错误假设，而非固定规则命中。
5. 报告、边界/失败样例、AGH 执行记录按赛事要求补齐。
