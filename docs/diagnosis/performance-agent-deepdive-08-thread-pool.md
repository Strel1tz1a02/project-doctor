# 问题八 深度解析：线程池 / 协程池争抢

> 本文回答三件事：①线程池/协程池争抢的**底层原因**；②如何通过**相关指标**诊断；③**为什么**这些指标能诊断（因果链）。

---

## 一、问题的本质

池的并发能力有限：要么**池太小**任务排队等，要么**任务在池内阻塞**占住执行单元，导致"CPU 不高但吞吐上不去"。

---

## 二、底层原因

### 2.1 根本机制：吞吐 = 池大小 / 平均任务耗时

池的吞吐上限由两个量决定：**并发单元数量**（池大小）和**每个任务的占用时长**。任何一个变差，吞吐就上不去——但**CPU 未必满**（因为任务可能是在"等"而非"算"）。

### 2.2 两种具体根因

| # | 根因 | 说明 | 特征 |
|---|---|---|---|
| 1 | 池太小 | 并发需求超过池上限，任务排队 | 队列持续积压、等待时间上升 |
| 2 | 任务阻塞 | 任务在池内做长阻塞调用（IO/睡眠），占住执行单元 | 队列不长，但单个任务耗时长 |

**派生的加重因素**：快慢任务混在同一个池里，少量慢任务就能堵住大量快任务（"一颗老鼠屎坏一锅汤"）。

> 根因链：任务阻塞往往不是终点——阻塞的可能是慢查询（问题一）、下游慢调用（问题六）等。分类出"阻塞"后还要追问"在等什么"，沿因果链继续回溯。

---

## 三、如何通过相关指标诊断

### 3.1 诊断指标清单

| 指标来源 | 指标 | 诊断信号 |
|---|---|---|
| **池指标** | 队列长度、任务等待时间 | 持续积压 / 上升 |
| | 活跃线程数 / 池大小 | 是否打满 |
| | 任务拒绝次数 | 增多 = 池爆了 |
| **应用指标** | CPU 使用率 | 不高（关键指纹） |
| | 吞吐（QPS/TPS） | 上不去 |
| | p99 延迟 | 上升（排队导致） |

### 3.2 诊断流程（关键在分类）

```
① 现象：CPU 不高，但吞吐上不去、p99 上升
        ↓
② 看池指标：队列是否持续积压？
   积压 → 池太小（供给不足）
   不积压但单任务慢 → 任务阻塞（占住执行单元）
        ↓
③ 对症：调大池 / 把阻塞任务移出主池、快慢分池
```

### 3.3 具体例子

线程池 10 个线程，任务里有一个对下游的 5s 阻塞 IO。并发上来后，10 个线程全被阻塞 IO 占住，后续任务排队，p99 从 50ms 涨到 5s+，但 CPU 使用率只有 20%。

诊断：CPU 不高 + 队列积压 + 单个任务耗时长 → 任务阻塞。修复：把阻塞 IO 改异步 / 丢到独立的 IO 线程池，主池只跑轻量任务。

## 四、为什么这些指标能诊断出该问题（因果链）

### 4.1 为什么"CPU 不高但吞吐上不去"是典型指纹

- 若是 CPU 密集问题，CPU 会打满；
- **CPU 不满却吞吐低**，说明任务大部分时间在"等"（排队或阻塞）而不是"算"。

这个矛盾（资源没满、产出却低）是指向"争抢/阻塞"的**决定性信号**，能把它和 CPU 密集问题区分开。

### 4.2 为什么队列长度能区分"池小 vs 阻塞"

- **池小**：供给不足 → 任务在队列里**持续积压**；
- **任务阻塞**：队列不一定长，但**单个任务占用时间长**，执行单元被"慢任务"占住。

所以"队列长度"和"单任务耗时"两个指标的组合，能把两种根因分开。

### 4.3 为什么任务等待时间是"供给不足"的直接度量

任务等待时间 = 从提交到真正开始执行的排队时长，是"执行单元供不应求"的**直接度量**。它上升，就说明池的供给跟不上需求，无论根因是池小还是阻塞。

### 4.4 为什么需要根因分类（而非只看等待时间）

等待时间只能证明"供不应求"，不能证明"池小还是阻塞"。而两者修法相反：池小 → 调大；阻塞 → 调大反而浪费资源，应该把阻塞任务移出。所以必须先分类再给方案——这也是它检测难度标"中"的原因。
