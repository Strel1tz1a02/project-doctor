# 问题一 深度解析：慢查询 / 全表扫描

> 本文是初版 9 个问题中第 1 个问题的深度解析，回答三件事：
> ①问题出现的**底层原因**；②如何通过**相关指标**诊断出该问题；③**为什么**这些指标能诊断出该问题（因果链）。
>
> 示例以 MySQL 为主，附 PostgreSQL 对应概念。

---

## 一、问题的本质

一条 SQL 本可以借助索引用 **O(log n)** 定位到目标数据，却退化成了**顺序扫描整张表**（O(n)）。数据量越大，这个退化的代价越大——这就是"慢查询 / 全表扫描"。

---

## 二、底层原因

### 2.1 根本机制：索引为什么能加速

- 表数据物理上以"数据页"为单位摊开存放，行与行之间没有查找结构。
- **没有索引**时，数据库要找到符合条件的行，只能从第一个数据页顺序读到最后一个，逐行比对——**全表扫描**，复杂度 O(n)。
- **索引**（通常 B+Tree）相当于给某一列建了"目录"：按值有序组织，能 O(log n) 定位到目标行所在的数据页，再从那个页取数据。
- 所以"慢查询/全表扫描"的本质是：**没有走索引这条捷径，退回了顺序扫描**。

### 2.2 导致慢查询 / 全表扫描的七类具体原因

| # | 原因 | 说明 | 典型例子 |
|---|---|---|---|
| 1 | 根本没建索引 | 过滤列上没有任何索引 | `WHERE nickname = 'x'` 而 nickname 无索引 |
| 2 | 索引失效（对列套函数/运算） | 对索引列做了运算，B+Tree 的排序结构无法利用 | `WHERE DATE(created_at) = '2026-09-30'` |
| 3 | 隐式类型转换 | 列类型与比较值类型不一致，数据库把列隐式转换后再比较 | `WHERE id = '123'`（id 是整数） |
| 4 | 前导通配符 | 通配符在最前，破坏最左匹配 | `WHERE name LIKE '%张'` |
| 5 | 复合索引没满足最左前缀 | 建了 (a, b, c) 索引，查询却只用 b 或 c 过滤 | 建 `(status, city)`，只查 `city` |
| 6 | 索引选择性差 / 回表代价高 | 列值区分度低，或返回行占比大，优化器认为"扫索引再回表"不如直接扫全表 | `status` 只有 2 种取值 |
| 7 | 统计信息过期 / 数据量增长 | 优化器靠统计信息估算成本，信息过时选错计划；或数据增长使原查询非线性变慢 | 大批量写入后未更新统计 |

> 其中 1～5 是"索引用不上"，6～7 是"有索引但优化器不选"或"原来不慢现在变慢"。这直接对应"性能回退"——第 7 类就是典型的**数据规模增长导致的隐性退化**。

## 三、如何通过相关指标诊断

### 3.1 诊断指标清单

| 指标来源 | 指标 | 含义 | 诊断信号 |
|---|---|---|---|
| **慢查询日志** | `Query_time` | SQL 总耗时 | 超过阈值（如 >1s） |
| | `Rows_examined` | 扫描（检查）的行数 | **远大于 Rows_sent** |
| | `Rows_sent` | 实际返回行数 | 很小 |
| | `Lock_time` | 锁等待时间 | 异常高（区分锁问题） |
| **DB 计数器** | `Slow_queries`（累计慢查询数） | 慢查询总次数 | 斜率突然上升 = 回退 |
| | `Handler_read_rnd_next` | 顺序扫描时"读下一行"的次数 | 持续增长 = 有全表扫描 |
| | `Handler_read_key` | 通过索引读的次数 | 相对偏低 |
| | `Select_scan` | 全表扫描次数 | 上升 |
| | 缓冲池命中率（read_requests vs reads） | 内存命中比例 | 下降 = 大量冷数据读盘 |
| **资源指标** | DB CPU 用户态、磁盘读 IO | 物理代价 | 慢查询发生时同步升高 |
| **APM/trace** | DB span 耗时 | 哪个 SQL 是热点 | span 耗时占比高 |
| **应用指标** | 接口 p99、错误率 | 现象层 | p99 上升、超时增多 |

**Agent 侧对照实验判据**（诊断引擎在隔离环境复测时额外采集/判定，与上表“提示性/现象”指标互补，是下结论的门槛）：

| 判据 | 采集来源 | 判定阈值 |
|---|---|---|
| 锁等待排除 | 语句 `LOCK_TIME`（逐语句实测表锁 + InnoDB 行锁，8.0.28+）+ MDL 全局汇总差值 | `lock_wait_ms == 0` 且 MDL 上界（`residual_ms`）不足以解释收益；< 8.0.28 时须行锁计数无增长 |
| 耗时可区分 | 同一 SQL 在基线 / 候选索引两组的重复样本 | 两组各自稳定（重复 ≥3，离散度用 IQR，容差 ≤ max(25%×中位数, 0.5ms 绝对地板)）且中位数差 > max(1ms, 两侧 IQR 之和) |
| 扫描工作量下降 | `Rows_examined`（performance_schema 实测） | 候选组中位数 < 基线组中位数 |
| 反例信号（分级） | 上述扫描量与耗时 | 扫描量未降且基线中位耗时 < 最小可区分差异 → `unclassified`（已有索引 / 数据过小，未复现） |

> 锁等待的“零等待证明”语义：`LOCK_TIME` 是逐语句权威指标，MySQL 8.0.28+ 含表锁与 InnoDB 行锁、不含 MDL。因此 `LOCK_TIME=0` 即实测表/行锁零等待；MDL 是唯一未测项，用全局 `wait/lock/metadata/sql/mdl` 汇总差值约束（`residual_ms`），不能冒充精确零等待。

> PostgreSQL 对应：`pg_stat_statements`（`mean_exec_time`/`rows`/`calls`）、`pg_stat_user_tables` 的 `seq_scan`/`idx_scan`、`log_min_duration_statement` + `auto_explain`。

### 3.2 诊断流程（现象 → 确认 → 定位根因）

```
① 现象：接口 p99 上升、DB CPU/IO 升高、Slow_queries 斜率陡增
        ↓
② 收敛：慢查询日志里取耗时最长、Rows_examined 最大的几条 SQL
        ↓
③ 确认：看 Rows_examined ≫ Rows_sent？→ 基本可判定"扫描行数异常"
        ↓
④ 核对访问路径：对 SQL 跑 EXPLAIN，结合实际执行统计看是否扫描大量行
        ↓
⑤ 排除锁等待：语句 LOCK_TIME 实测表/行锁为零（8.0.28+）+ MDL 全局汇总差值约束
        ↓
⑥ 对照实验：隔离环境基线 vs 候选索引，重复采样比较耗时与扫描量（尺度适配波动 + 最小差异）
        ↓
⑦ 定位根因与反例分级：结合表结构、数据分布和代码位置区分原因；
   扫描量未降且基线本就不慢 → unclassified；扫描量未降且基线仍慢 → 继续排查其它根因
```

### 3.3 一个具体例子

表 `users` 1000 万行，`last_login` 无索引，查询：

```sql
SELECT * FROM users
WHERE status = 'active' AND DATE(last_login) = '2026-09-30';
```

慢查询日志记录：

```
Query_time: 8.2s
Rows_examined: 10,000,000
Rows_sent: 3
```

EXPLAIN 结果：

```
type: ALL   key: NULL   rows: 10,000,000
```

诊断结论：
- `Rows_examined / Rows_sent = 10,000,000 / 3` → 提示本次查询检查了大量行；
- `type=ALL, key=NULL` → 本次计划使用全表扫描，未使用索引；
- 待验证原因：`last_login` 没有索引，`DATE(last_login)` 也不利于使用该列的范围索引；还需核对数据分布与代码调用位置；
- 候选建议：评估为 `last_login` 建索引，并改写为范围条件 `last_login >= '2026-09-30' AND last_login < '2026-10-01'`；在隔离环境复测收益与代价后再下结论。

### 3.4 信号分层与共存判别

本问题的信号分两层，避免把"提示"当"结论"：

| 层次 | 信号 | 说明 |
|---|---|---|
| 提示性 | `Rows_examined ≫ Rows_sent`、`Slow_queries` 增长 | 只能说明"扫描过多"，**全表扫 / 范围扫 / 深分页都会这样**，不能单凭它下结论 |
| 访问路径 | `EXPLAIN` 的 `type=ALL`、`key=NULL` | 表明这次计划选择了全表扫描；是否构成性能问题，还需结合实际耗时、数据规模和对照实验 |
| 证据门槛（结论） | 锁排除 + 对照实验（耗时/扫描量） | 锁等待排除 + 扫描量下降 + 耗时可区分 → `verified`；证据不足 → `lead`；扫描量未降且基线不慢（已有索引/数据过小）→ `unclassified` |

三路结论（避免把“没复现”误报成“没找到根因”）：
- **verified**：锁已排除、候选索引确实降低扫描量、且耗时下降超过测量噪声与最小差异——正例诚实定级；
- **unclassified**：扫描量未降、且基线 SQL 耗时已低于最小可区分差异——说明慢查询/全表扫描在当前数据与代码下**未复现**（已有可用索引或数据量过小），不下“缺失索引”的结论；
- **lead**：证据不足（锁/证据链/结构失败），或扫描量未降但基线仍慢（根因未解决）——继续采集或排查其它原因。

共存判别（与深分页区分，见问题四）：全表扫描与深分页用**各自独立**的信号判定，不必用 `type` 二选一——因为深分页本身也可能是 `type=ALL`（排序列无索引时）：
- 全表扫描候选 → EXPLAIN `type=ALL`（访问路径扫整表）；
- 深分页候选 → SQL 文本含大 `OFFSET`（与访问路径无关）。

一条 SQL 可以两者都有（`type=ALL` 且带大 `OFFSET`），此时全表扫描主导、OFFSET 被淹没，修复顺序先全表扫、复测后再处理 OFFSET。

## 四、为什么这些指标能诊断出该问题（因果链）

### 4.1 为什么 `Rows_examined ≫ Rows_sent` 能提示"扫描过多"

SQL 执行的本质是"**检查行 → 匹配 → 返回**"。`Rows_examined` 度量的是"引擎为了返回结果，一共触碰/比对了多少行"。

- 索引的作用，**恰恰就是缩小"需要检查的行数"**。
- 走索引时：B+Tree 定位到少数页 + 少量回表 → `Rows_examined` 接近 `Rows_sent`。
- 全表扫描时：引擎逐页读、逐行比对 → `Rows_examined` 约等于整表行数，而 `Rows_sent` 可能只有几行。

因此这个比值只能提示本次查询检查的行数较多；要确认访问路径，需结合该 SQL 的执行计划。访问路径为全表扫描也不自动等于性能缺陷，仍需验证其实际代价。

### 4.2 为什么慢查询日志能定位到具体 SQL

指标（如接口 p99）是**聚合的、无上下文的**，只能告诉你"慢了"，不能告诉你"慢在哪"。而 SQL 是性能问题的**最小可定位单元**，慢查询日志把"慢"绑定到"SQL 文本 + 执行统计"上，是定位的原子证据。

### 4.3 为什么 `Handler_read_rnd_next` / `seq_scan` 能暴露全表扫描

`Handler_read_rnd_next` 等计数器能提示顺序读取活动，但它们通常是聚合指标，不能单独归因到目标 SQL。应结合请求关联的 SQL、执行计划和实际执行记录判断。

### 4.4 为什么 DB CPU / 磁盘 IO / 缓冲池命中率能佐证

全表扫描的物理动作是：把大量数据页从磁盘读进内存、逐行 CPU 比对。这三个指标分别是这个物理动作的三个投影：

- **磁盘读 IO 升高**：要读的页多了；
- **缓冲池命中率下降**：大量页是"读一次就扔"的冷数据，无法命中内存缓存；
- **CPU 用户态升高**：逐行比对是 CPU 密集操作。

这些变化可能作为旁证，也可能被缓存状态和其他负载掩盖；不能要求它们必然同步出现。

### 4.5 为什么需要 EXPLAIN 与实际执行证据

指标/日志提供耗时与检查行数，EXPLAIN 给出优化器的计划访问路径；估算行数不等于实际行数。要确认根因及影响，还需把目标请求、具体 SQL、触发代码与实际执行结果关联，并在可比条件下验证候选改动。

### 4.6 为什么能进一步区分"没建索引" vs "索引失效"

`key=NULL` 只说明"这条 SQL 没用上索引"。再往下定位：

- 查表结构：过滤列上**根本没有索引** → "没建"；
- 过滤列上**有索引**但 `key=NULL` → 可能是谓词不适用，也可能是数据分布使全扫更划算；检查谓词、索引定义、统计信息和实际代价后再判断。

## 五、对 Agent 模块的落点

本问题的诊断链正好映射到既有模块：

```
M1 指标采集（p99/CPU/Slow_queries 突变）
  → M2 基线管理（判定是否回退）
  → M3 慢查询解析器（Rows_examined/Rows_sent、SQL 文本）
  → M8 执行计划分析器（EXPLAIN：type/key/rows）
  → M7 代码分析器（回溯生成 SQL 的代码位置）
  → M10 优化模板库（加索引 / 改写 SQL 模板）
  → M12 复测执行器（该 SQL 耗时、慢查询数下降）
```

诊断引擎侧配套（本次补齐，落在 `run_experiment` 现有采集内，不新增 MCP 工具）：

```
  → 锁证据探针 lock_probe（LOCK_TIME 逐语句实测表/行锁 + MDL 全局汇总差值，产出「MDL 上界」）
  → 测量策略 MeasurementPolicy（重复次数、IQR 离散度 + 0.5ms 绝对地板、最小可区分差异）
  → 反例分级 slow_query（verified / lead / unclassified 三路结论）
```

其中 M3 的 `Rows_examined/Rows_sent` 比值、M8 的 `type/key`，就是本问题最关键的两个诊断信号——它们的"为什么"分别在 4.1 和 4.5 中说明；`lock_probe` 与 `MeasurementPolicy` 则对应第 3.1 节新增的对照实验判据与第 3.4 节的证据门槛。
