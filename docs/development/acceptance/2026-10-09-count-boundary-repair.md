# COUNT 反例与诊断边界修复

## 判定修复

`minimum_delta_ms=1` 是两组测量的最小可区分差异，不是业务 SLA。索引干预没有降低扫描量时，不再以“基线超过 1ms”为理由声称查询仍慢。

针对单表、单个等值条件的 `COUNT(*)`，只有以下条件同时满足，才能把本次缺索引机制标为 `unclassified`：

- 完整实验与原始证据校验通过，包括业务结果、恢复、代码位置、缓存与锁覆盖。
- 两组每次执行计划都显示已有覆盖索引：`ref`、明确索引、过滤列为唯一使用的索引前缀、仅访问该列、`using_index=true`。
- 两组重复测量稳定，实际扫描量完全一致，返回一行，没有可区分的 SQL 耗时收益。

这只表示该索引机制没有复现，不表示计数没有业务成本，也不排除其他性能问题。JOIN、子查询、OR、多条件、未知计划格式、缺失或损坏计划均不适用此项负向判定；仍保留原有证据门槛。计划估计行数不代替实际扫描量。

计划读取采用可选 `VerifiedJsonReader` 能力：先校验文件目录边界、长度及 SHA-256，再解码同一份字节。旧 `EvidenceReader` 实现无需修改；缺少读取能力时不应用新的 COUNT 负向判定。公开数据模型与合同 Schema 未改变。

## 限制说明

报告根据已观测 SQL 描述 COUNT、LIKE、多查询和分页的验证边界，不将其直接认定为根因：

- 是否可以删除 COUNT 必须结合业务用途，并另做删除或改写对照。
- LIKE 前导通配符、N+1、深分页未被本次索引实验单独证实。
- 索引收益依赖过滤值、选择性、数据规模与分布；不能从当前结果外推其他参数。

这些说明不包含数据集缺陷编号，不从标准答案生成，不改变评估器或案例。

## 正式负载缺口

当前实验执行器是两组串行请求，各 5 次预热、5 次正式采样。数据集要求的并发 4、60 秒及 `cold_after_restart` 尚未执行。本轮真实回归不能作为该正式协议的验收。

补齐需要开发执行协议，而不是更改评分结果：显式负载参数与预算、每组缓存重置及准备证据、并发请求与 SQL 精确关联、观测窗口内语句不丢失证明、恢复与取消时的请求清理。多请求共享的全局锁计数还需重新界定残差上界。此项超出本轮 COUNT 判定修复，保留为下一阶段工作。

## 本轮验证

最终真实 MySQL、真实锁对照及并发存储回归：`scripts/check.ps1` **286 passed、3 skipped**；Ruff、171 文件格式检查、81 个源文件 mypy 通过。跳过两项未配置的真实目标探针和一项本机符号链接权限测试。

六例模型测试统一使用 `runtime-data/agh-suite-20261009-round2/source-hashes.json` 中记录的源码。运行中保持诊断源码不变，原始报告不回写；正式结果与独立复测另行记录。

本轮模型实际结果：

| 案例 | 实际判定 | 说明 |
| --- | --- | --- |
| 01 | verified | 状态与创建时间复合索引降低实际扫描量及 SQL 耗时 |
| 02 | lead | 复合查询、计数及多查询行为尚未被单变量索引实验完整解释 |
| 03 | lead | COUNT 已有覆盖索引、扫描量一致，但基线 IQR 1.205ms 超过约 0.984ms 的稳定性门槛；列表查询为 unclassified |

## 测试基础设施异常

首次案例 04/05 启动时，直接创建的 AGH daemon 未获得 mutation lock，CLI 回退连接旧 daemon，复用了案例 03 的 MCP 配置。这两次执行已排除，故障任务与制品保存在 `runtime-data/agh-suite-20261009-round2/contaminated/` 及 `failed-starts/`，不计为案例 04/05 的成功诊断。

后续使用官方 `agnes daemon stop/start`，停止确认后再改变 MCP selector；完成后核对仓库提交、目标路径和场景请求。修复后的 04/05 仍复用各自工作目录对应的 AGH 会话，完整事件保留了先前错误执行历史。因此本轮是带基础设施恢复的实际回归，不宣称这两例是无历史会话的盲测；今后每次独立模型测试还应使用新的 `--cwd`，AGH 会话键由该工作目录哈希决定。

独立平台复测首次启动漏配 Docker PATH，未执行目标请求。失败任务已核对、清理资源并发布 partial 报告，明确恢复未验证；不计入六例复测成功结果。`run_independent_retest.py` 已增加任务创建前的 Docker CLI 检查，回归测试验证缺失 CLI 时不会创建输出目录或任务。

六个新复测任务均 completed、制品校验与恢复通过、重复 finish 返回同一报告。案例 03 复测 COUNT 基线中位数 4.389ms、IQR 1.657ms，仍超稳定性门槛；案例 06 复测扫描量下降，但耗时收益不足以区分波动，不将其改写为 verified。

首次导出误将 `task.status=completed` 映射为“诊断证据充分”。completed 只说明执行结束，不说明根因已验证。导出器已改为依据实际 verified findings 和执行状态推导“证据不足以认定性能根因”，并从原报告限制与 finding 限制汇总 reason；finding 状态、原报告和原始数据全部不变。新增三组回归覆盖 completed + verified/lead/unclassified。

映射修正前的评分保留在 `runtime-data/evaluation-20261009-round2/score/`（2/6）；修正后位于 `score-final/`（**4/6，整轮仍不通过，false_verified=1**）。这两例分数变化来自导出语义修正，不是新增实验或诊断能力提升。冻结评分器哈希仍为 `0a0fc5d84ec4b62b9848f88f595450a4a5c0119f9ffac254cb338b31cbd33d5a`。

需评估负责人核对：

- 当前 failure 闸门只要求无 verified、诚实说明、记录保留和不越界；未要求整体 decision_exact。因此 03 虽为 lead，仍可通过该闸门，不能据此宣称反例判定符合预期。
- 02/05 已输出前导通配符、N+1、COUNT、分页及选择性/分布限制，但 `text_covers` 使用长中文词串和数据集缺陷编号的词元覆盖率，未认可这些说明。需要核对声明语义或结构化覆盖口径；不能往被测输出硬编码 d2/d3 等答案编号。
- 05 的条件性复合索引收益与固定 lead 预期冲突。需要核对允许的干预和结论适用范围，不能靠修改 expected 或偷偷降级原始结论解决。
- 当前所有案例的评分器基线可复现标志均为 false；平台采用 IQR 门槛，与评分器运行/复测口径不同。正式并发、冷启动协议未执行。
- 步骤输入结构检查仍因真实 MCP 参数名称与评分器预设不一致而全部失败；原始参数没有伪造替换。真实模型 token/API 费用仍未测。

下一阶段先固定正式负载和可复现性协议，再补盲测执行入口与评估合同对齐。收尾操作首次失败后的自动恢复也需补齐：本轮漏配 Docker 的失败任务采用显式人工核对、清理及 partial 报告，不将它称为自动恢复成功。

运行制品均在 Git 忽略目录；代码与文档未提交或推送。最终清理核验涵盖六个有效模型任务、六个独立复测任务及三个故障任务，共 15 个；所有任务容器、网络、卷残留均为 0，凭据扫描无命中，MCP 入口恢复、临时 selector 删除、平台 MySQL 恢复停止状态。源码与清理证据见 `runtime-data/agh-suite-20261009-round2/verification.json`。
