# Docker 恢复后的持续负载评估

状态：六例诊断评估已完成，诊断门槛通过 1/6，整轮未通过。

## 协议与边界

六个公开慢查询案例分别使用全新 AGH 会话；模型只接收公开源码和通用受控索引配方库存。
每例最多一次索引实验，基线与候选组分别重启应用和数据库，预热 10 秒，以并发 4 测量 60 秒。
用户在模型阶段结束后明确范围：只评诊断，不评修正。
诊断中的受控索引对照仍作为证据实验；修正收益、修正后业务正确性和额外修正复测不进入评分。
评分复用冻结数据集的指标，只排除 `recommendation_effective`、`correctness_preserved` 两项指标和门槛；
保留原根因、代码位置、证据、过程、成本、误验证和诊断实验恢复要求，不修改标准答案。

每组只有一个持续负载窗口。窗口内数千个 HTTP 请求不能当成三次以上独立负载重复。
目前持续负载证据是 HTTP 耗时和业务断言，缺少完整逐 SQL 与锁关联，因此不能验证 SQL 根因。

原始记录保存在 Git 忽略目录 `runtime-data/timed-evaluation-20261009-live/`。

## 本轮阻塞与修复

前三次模型尝试均在创建任务时 Git 校验失败，没有创建诊断任务。
本地最小 MCP 服务复现出 Git 子进程继承 MCP 标准输入后超时；指定 `stdin=DEVNULL` 后，
同一复现中的同步与线程校验分别耗时约 0.185 秒、0.165 秒，均成功。
源码校验还改为解析绝对 Git 可执行路径，并在错误中记录失败子命令和错误类型。

私有评估提示截取曾命中正文中首次出现的“待测源码”，导致旧预算与计次预热要求混入。
现按源码 README 标题截取，仅保留新协议及公开源码；失败尝试分别归档，未改写日志。

自动审批服务曾返回 403，阻止验证命令执行；恢复后 Ruff 检查与相关 15 项测试通过。
默认回归检查：319 项通过、12 项跳过；Ruff 检查与格式、mypy（81 个源文件）通过。
跳过项包含未配置启用条件的真实数据库、锁和目标探针，不能算作这些能力的实测通过。
