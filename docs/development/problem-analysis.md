## 一、证据链的「完整性幻觉」——把部分观测当成完整证明

这是本项目暴露得最集中、也最核心的一类问题。共同根因是：

> **采集器只能证明「观察到了什么」，却把「没观察到」当成了「没有」；
> 证据的身份维度不足；用近似值去满足判定门槛。**

### 1.1 锁等待证据不完整却标为零

- **现象**：`LOCK_TIME` 只覆盖表 / 元数据锁，**不含 InnoDB 行锁**，却作为 `lock_wait_ms` 的
  actual 来源；还把 <0.05ms 的非零值舍入为 0，使 B 的零等待门槛形同虚设。
- **根因**：把「表锁覆盖」误当「完整锁覆盖」；用**舍入**掩盖真实等待，而不是补证据。
- **解决**：
  1. `LOCK_TIME` 不再冒充完整 `lock_wait_ms`，未知保持 `null`；
  2. 独立 `lock_probe.py` 采样 `data_lock_waits`（行锁）+ `metadata_locks`（元数据锁），
     按 request_id / THREAD_ID / EVENT_ID 关联，只输出 `observed` / `unknown`、覆盖 `partial`；
  3. **空快照绝不等于零等待**，`covered_no_wait` 需要全区间覆盖证据（`models/lock.py` 的校验器强制）。

### 1.2 SQL 无法归属到本次请求

- **现象**：探针查询 `events_statements_history_long` 最近 64 条标记 SQL，没有请求标识、线程关联或
  请求前后水位；串行 HTTP 会混入历史 SQL。
- **根因**：依赖「最近 N 条」的时间窗近似，无法**证明**请求关联。
- **解决**：目标侧经 `RequestIdFilter` + MyBatis 拦截器给每条 SQL 注入
  `/* pd:<路径>:<行号> request=<32 位十六进制 ID> */`；探针只查询、解析本次 ID；平台在查询与解析两阶段核验 ID。

### 1.3 相同内容的制品跨路径冲突

- **现象**：`artifact_id` 只取内容哈希，同样的 EXPLAIN 计划写入 baseline 与 candidate_index
  不同路径时返回同 ID 不同元数据，B 的 evidence 校验抛「同一制品元数据冲突」。
- **根因**：内容寻址漏掉了「路径 / 媒体类型 / 格式版本」这些**身份维度**。
- **解决**：`artifact_id` 改为对「路径 + 媒体类型 + 格式版本 + 内容摘要」共同取哈希；`sha256` 继续表示内容。

### 1.4 含未知 `?` 参数的 SQL 生成替代参数计划

- **现象**：把所有 `?` 替换成 0 生成 EXPLAIN，产出的是替代参数计划，却被当成实际请求参数的计划。
- **根因**：在缺少绑定参数证据时仍「硬生成」计划。
- **解决**：无实际绑定参数证据就不生成计划，缺失由 B 降级为线索。
  （真正的正解随后在真实联调中被验证：MySQL Connector/J 默认客户端预编译，SQL 值已内联，计划天然忠实。）

### 1.5 指纹与预算的完整性

- **指纹**：观测指纹直接填 `spec.baseline_fingerprint`，未核验观测时的实际环境状态；candidate_index 也填相同值。
  → 改为观测前后从**实际 dump** 计算指纹，不匹配或观测中变化即失败并恢复。
- **预算**：`artifact_bytes` 只统计恢复引用，漏掉观测原始统计与计划制品。→ 完整计入。

**沉淀原则**：**「证明缺失 ≠ 缺失」「空 ≠ 零」「近似 ≠ 证据」**。宁可降级为线索 / 不生成，也不伪造完整证据。

## 二、状态机与幂等的语义错位——把「存在 / 同键」当成「有结果 / 可重放」

共同根因：

> **状态分类维度不足：把「记录存在」当「有最终结果」，把「同操作键幂等」当「任务终态保护」，
> 取消 / 失败路径没有终态落库，也没有跨请求互斥。**

### 2.1 中断操作被判成完成

- **现象**：真实 store 对 reserved / running 记录也返回 OperationResult（即使无 `result_json`），
  reconcile 把「对象存在」等同于「已有最终结果」，中断任务被判 completed。
- **根因**：分类不按「终态 + 持久化结果」，只按「记录是否存在」。
- **解决**：`classify_operation` 按终态与持久化结果分类——有结果=completed、仅 reserved 无结果=safe_same_input、
  否则 needs_reconcile；running 无结果进入 unresolved 并持久化隔离。

### 2.2 首次准备取消后状态不可恢复

- **现象**：prepare-1 取消后保留 running/reserved，reconcile 返回 unresolved，后续同业务键拒绝执行；
  容器还活着但没有 environment_id 和基线快照，任务卡死。
- **根因**：取消路径没有把「失败 + 已清理」作为终态落库。
- **解决**：取消 / 异常结算实际墙钟时间、持久化原因、清理成功写 `failed`、清理未知保持 `needs_reconcile`；
  `finish_task` 即使无 environment_id 也按任务 Compose 标签拆除资源。

### 2.3 模型重复尝试未知操作

- **现象**：模型得到 unresolved / quarantined 后仍重试相同键，并换 prepare-2/3/4 绕过。
- **根因**：程序没有拒绝「在未解决的准备操作上新建并行准备」；指令也未约束此时只能收尾。
- **解决**：MySQL 对任务加**行锁**，同任务存在 reserved/running/needs_reconcile 时新 prepare ID 无法绕过互斥；
  指令明确此时只收尾，不能用换 ID 绕过未知状态。

### 2.4 finish 后的任务终态保护缺失

- **现象**：finish-1 成功 completed 并拆除容器，模型继续 finish-2/3 收尾，平台恢复已停 DB 失败，任务降为 partial。
- **根因**：「同操作 ID 幂等」不能替代「任务已到终态后禁止再恢复 / 收尾」。
- **解决**：任务终态保护（完成态拒绝后续恢复 / 收尾操作）。此点已识别，列为后续修复项。

**沉淀原则**：**「存在 ≠ 有结果」「同键幂等 ≠ 终态不可变」「互斥要落到存储层」**。

## 三、跨层生命周期与超时不统一——系统边界由最弱一层决定

共同根因：

> **AGH SDK、MCP、平台工具、Docker 各层对「超时 / 取消」的语义不一致；
> 取消是协作式的，不会抢占正在进行的后台操作；失败路径绕过了预算结算。**

### 3.1 MCP 长操作超时未对齐

- **现象**：平台工具允许 600 秒，但 AGH 的 `conn.callTool` 底层 MCP JS SDK 约 60 秒超时；
  应用还在初始化时 `prepare_environment` 被取消。
- **根因**：端到端调用超时各层各自为政，**最弱的 60s 成了事实边界**。
- **解决**：`agh/apply_timeout_patch.py` 把 SDK 等待调到 660s、三个长工具 preset 上限 720s、
  平台预算 600s；只改本次 `pd` 长工具，不动其他工具默认值。

### 3.2 双层取消与「取消 ≠ 立即停止」

- **现象**：第一轮修复后又遇 AGH 120s 执行限制，并暴露 AnyIO **重复取消**；取消后 Docker 不会立即停止。
- **根因**：取消信号会多次到达；后台线程 / 容器在取消后仍在运行。
- **解决**：Docker 准备线程用 `shield` 等待，取消后在 AnyIO 屏蔽作用域内**等原线程结束再 teardown**；
  结算实际墙钟时间（真实案例 337.233 秒），证明「取消等待是等后台操作结束，不是立即 kill」。

### 3.3 失败路径预算未完整结算

- **现象**：实际准备等待约 60 秒，持久化的 `Usage.wall_seconds` 仅约 0.0102。
- **根因**：取消 / 异常路径绕过了结算逻辑。
- **解决**：操作异常 / 取消也结算实际墙钟时间、持久化原因并进入报告。

**沉淀原则**：**「边界取各层最小值，要么统一要么显式分层」「取消是协作不是抢占」**。

## 四、平台与目标环境的边界特性——逻辑正确 ≠ 真实环境能跑

共同根因：

> **OS / 框架 / 数据库的隐含约束只在真实联调时暴露；单测和假实现覆盖不到。**

### 4.1 Windows 源码复制清理失败

- **现象**：gateway 复制 `.git`，重试时 `shutil.rmtree` 遇只读 `.git/objects` 触发 WinError 5。
- **解决**：工作副本排除 `.git/.hg/.svn`，保留提交与复制前业务文件哈希；旧副本只读文件清理受路径检查约束。

### 4.2 种子初始化极慢

- **现象**：20 万订单种子 5 分钟仅 3 万条。
- **根因**：JDBC 缺 `rewriteBatchedStatements=true`，逐条往返 + 每次 fsync。
- **解决**：独立运行副本 JDBC URL 增加该参数，20 万订单写入降到 ~11 秒；只优化种子写入，不作为索引干预变量。

### 4.3 网络隔离退化

- **现象**：`internal: true` 静默禁用端口发布，`18080:8080` 为空。
- **解决**：普通桥接网络；独立入口仅绑定 `127.0.0.1` 固定转发到 app:8080，应用与数据库只连内部网络。

### 4.4 AGH 工具前缀超长

- **现象**：目录接入用较长服务名 project-doctor-probe，AGH 生成的工具 prefix 超过 extension-manifest
  Schema 的 33 字符限制，挂载失败。
- **解决**：改短名 `pd`。

### 4.5 模型把对象参数编码成字符串

- **现象**：模型把引用 Schema 的对象参数编码成字符串，工具校验拒绝，任务未创建。
- **解决**：临时适配器把 `$defs/$ref` 展开成自包含 Schema，语义校验仍由原业务模型执行；
  这是测试设施缺陷，不算产品诊断失败。

### 4.6 受控配方引用越界

- **现象**：`runtime_factory` 接受直接 CREATE 文本，recipe 名称未做路径包含校验。
- **解决**：强制 `recipe:` 受控引用 + 路径包含校验，拒绝直接 SQL 和越界路径。

### 4.7 评估器浮点取整不一致

- **现象**：本地评估器冻结均分 0.8895 与 `round(0.88945, 4)=0.8894` 不一致。
- **解决**：统一取整语义（数据与期望未修改）。

**沉淀原则**：**真实联调是唯一能暴露平台边界特性的手段；单测通过 ≠ 端到端可用。**

## 五、诊断判据的边界与模型约束——严格、诚实，但还要更完整

这一类是「门槛本身设计正确」带来的问题：系统没有为了出「好看的结果」而放松规则，但配套能力还不完整。

### 5.1 正例扫描耗时均降，仍不能 verified

- **现象**：case-01/04 索引后扫描量从 200020 降到 20/3、耗时从 45.6/50.2ms 降到 0.53/0.27ms，
  但结论仍是 lead。
- **根因**：锁覆盖只有 partial，且基线 / 候选组的相对极差超 0.25 波动门槛。
- **解决方向（后续）**：完善**可靠锁证据**与**重复测量**以压缩波动；**不放松证据门槛换 verified**。

### 5.2 反例没有归为 unclassified

- **现象**：case-03（已有可用索引）、case-06（300 条数据无收益）仍被输出为 lead，而不是 unclassified。
- **根因**：诊断规则缺「反例分级」——「已有索引 / 数据量太小 / 收益不显著」应归为「该问题不成立 / 未复现」。
- **解决方向（后续）**：增加反例分级，把「无显著改善」与「尚未证明」区分开。

### 5.3 模型自由文本的事实误读

- **现象**：case-06 模型总结称「耗时降低、缺索引为主因」，但实际中位耗时 0.307 → 0.358ms、扫描量 320 → 320。
- **根因**：模型文字不被结构化对照值约束，可以「说错话」而程序不阻止。
- **解决方向（后续）**：报告生成用**结构化对照值**约束模型表述，程序保留 lead 不被误升。

### 5.4 会话与工具的自动关联缺失

- **现象**：报告缺 `agh_session_id`、`tool_call_id`；独立 session.jsonl 与工具日志可追溯，但未自动关联。
- **解决方向（后续）**：把 AGH 会话 / 调用 ID 自动写回报告。

**沉淀原则**：**程序结论优先于模型文字；门槛为真就不妥协，宁可 lead 也不伪证 verified。**

## 6. 方法论沉淀（可复用的原则）

1. **证明缺失 ≠ 缺失**：采集器只报告「观察到什么」与「覆盖范围」；没覆盖到的，明确未知。
2. **空 ≠ 零**：空快照、空结果都不能反向推出「零等待」「无影响」。
3. **近似 ≠ 证据**：舍入、最近 N 条、占位符参数都不能当作证据去满足门槛。
4. **存在 ≠ 有结果**：状态判断看「终态 + 持久化结果」，不看记录是否存在。
5. **同键幂等 ≠ 终态不可变**：任务到达终态后，禁止用新操作 ID 重放恢复 / 收尾。
6. **互斥落到存储层**：并发 / 重复操作的防绕过靠数据库行锁与唯一键，不靠「先查后写」。
7. **边界取各层最小值**：跨层超时要么统一，要么显式分层；取消是协作不是抢占。
8. **真实联调是唯一裁判**：平台边界特性、种子速度、前缀长度这类问题，单测和假实现都暴露不了。
9. **门槛为真就不妥协**：不放松证据门槛换 verified，不靠模型文字补结构化事实。
