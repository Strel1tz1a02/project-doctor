# 性能诊断 Agent · 问题通俗解析 + 模块化功能设计

> 本文档做三件事：①用通俗语言解释初版要处理的 9 个问题；②为每个问题给出具体解决方案；③设计 Agent 的**模块化功能**，并说明每个解决方案如何通过"调用这些模块"来实现。

## 一、九个问题的通俗解释 + 具体解决方案

### 1. 慢查询 / 全表扫描

**通俗解释**：数据库要找东西，本该用"目录"（索引）快速定位，结果却大量翻页比对（**扫描过多**）——最常见的表现是从第一页一页页翻到最后（全表扫描）。数据越多，翻得越久。

**为什么 Agent 需要解决它**：数据库层最高发、影响最大的瓶颈，一条慢 SQL 就能拖垮整个接口乃至数据库；排查要在日志、执行计划、代码三处来回跳，Agent 能自动解析 EXPLAIN 并直接给出索引/改写建议。

**具体解决方案**：
1. 从慢查询日志挑出耗时最久、`Rows_examined`（扫描行数）最大的几条 SQL；
2. 每条跑 `EXPLAIN`，按**访问方式**定位"扫描过多"的根因：`type=ALL`（全表扫描，最常见）、`type=range`（大范围扫描）、`type=index`（全索引扫描）、或 `type=ref` 但选择性差导致回表多；
3. 对症下药：
   - 没索引 → 给过滤列建索引，如 `CREATE INDEX idx_user_status ON users(status)`；
   - 索引失效 → 改写 SQL 去掉列上函数/隐式转换，如 `WHERE DATE(created_at)=...` 改成 `WHERE created_at >= ... AND created_at < ...`；
   - 范围过大 / 选择性差 → 缩小查询范围、建复合索引、覆盖索引；
4. 复测：该 SQL 平均耗时 ↓、`Rows_examined` ↓、慢查询条数 ↓。

### 2. N+1 查询

**通俗解释**：本来一次能查完，却在循环里一条条查。像取 100 个快递跑 100 趟，而不是一趟拉一车。

**为什么 Agent 需要解决它**：最隐蔽的隐性回退——功能完全正确、单条查询也很快，只有看 trace 才能发现"查询次数爆炸"；且随数据/关联数增长非线性变慢，Agent 靠 trace 聚合 + 代码反模式能自动识别。

**具体解决方案**：
1. 在 trace 里发现同一请求出现大量同构小查询（这只是**提示**）；
2. **证明**：确认这些同构查询的参数来自主查询返回的对象集合，且查询次数随主对象数量线性增长（N 个对象 → N 条关联查询），并定位到"循环内调查询"的触发代码；
3. 改成批量：`WHERE id IN (1,2,...,100)`，或 ORM 预加载——`selectinload` 为"主查询 + 1 条 `IN` 关联查询"共 2 条、`joinedload`（JOIN）为 1 条但父行会重复需去重；
4. 复测：单请求查询次数从 N+1 降到 1～2 次。

### 3. 连接池耗尽 / 泄漏

**通俗解释**：连接像餐厅座位，数量固定。有人吃完不走（泄漏）、有人点菜磨蹭占座（慢查询），后面的人只能排队干等。

**为什么 Agent 需要解决它**：表现为大量请求超时/失败而非单纯变慢，直接损害可用性；根因有多种（泄漏/池小/慢查询），人工容易"只调大池"掩盖问题，Agent 能先分类根因再对症下药。

**具体解决方案**：
1. 看指标：活跃连接数是否打满、获取连接等待时间是否飙升、有无 `timeout waiting for connection` 日志；
2. 分三种根因对症下药：
   - **泄漏**：连接获取后没在 `finally` 里释放 → 修释放逻辑；
   - **池太小**：活跃数长期接近上限 → 调大池（如 `pool_size` 10→50）；
   - **慢查询占满**：连接都被慢 SQL 占着 → 这是**症状**，根因在问题 1（慢查询），回到问题 1 压慢查询，而不是盲目调大池；
3. 复测：获取连接等待时间 ↓、timeout 消失。

### 4. 深分页（大 OFFSET）

**通俗解释**：翻书翻到 1000 页，得先把前 999 页都翻一遍。用"书签"直接翻到上次停下的位置。

**为什么 Agent 需要解决它**：随数据增长翻后面的页越来越慢，是"数据规模增长隐性退化"的典型；排查成本极低但极容易被忽略，Agent 能从 SQL 里直接识别大 OFFSET。

**具体解决方案**：
1. 判据：直接看 SQL 文本里的大 `OFFSET`（如 `LIMIT 20 OFFSET 100000`）——与 `type`（访问方式）无关，深分页也可能 `type=ALL`；
2. 改成 keyset 分页：`WHERE id > 上次最大id ORDER BY id LIMIT 20`，用游标/书签代替 OFFSET；
3. 若业务必须支持跳页，限制最大页数；
4. 若同一 SQL 同时有全表扫描（`type=ALL`），先修全表扫描、复测后再处理 OFFSET（迭代诊断）；
5. 复测：深页查询耗时大幅 ↓。

### 5. 响应体过大

**通俗解释**：快递盒子超大，里面东西很小，还塞了一堆用不上的包装、没压缩、一次全塞进去。

**为什么 Agent 需要解决它**：拖慢所有用户（传输时间 + 带宽），且与功能无关、纯属"多传了用不上的东西"；优化简单、收益直接，Agent 能自动对比接口找出冗余字段。

**具体解决方案**：
1. 看指标找出响应体最大的接口；
2. 三件事按需做：
   - **压缩**：开 gzip/brotli；
   - **裁剪**：接口只返回必要字段，去掉冗余嵌套；
   - **分页**：大列表分页返回；
3. 复测：平均响应体大小 ↓、传输耗时 ↓。

### 6. 每请求新建连接

**通俗解释**：每次打电话都重新拨号、等对方接起来，而不是保持一条热线。

**为什么 Agent 需要解决它**：TCP/TLS 握手开销在微服务/外部依赖多时被成倍放大；属于一行代码级别的低级错误，Agent 能从 trace 建连占比 + 代码反模式直接定位。

**具体解决方案**：
1. 在 trace 里看"建连耗时（TCP/TLS 握手）"占比是否过高；
2. 代码里找"每次调用都 new 客户端"的地方；
3. 改成：HTTP 客户端用连接池 + keep-alive、客户端实例全局复用（不要每次请求新建）；
4. 复测：建连耗时占比 ↓、平均延迟 ↓。

### 7. 同步日志过多

**通俗解释**：每说一句话就立刻写进本子、写完才说下一句，话一多就卡。改成攒一批再写。

**为什么 Agent 需要解决它**：日志是"看不见的税"，每条同步刷盘都在拖慢请求却没人注意；高负载下被显著放大，Agent 能定位高频日志点并给降级方案。

**具体解决方案**：
1. 看日志吞吐/写耗时，找出高频日志点；
2. 三招按需上：
   - **异步日志**：不阻塞业务线程；
   - **降级别**：生产环境关掉 debug 级别；
   - **采样**：高频日志按比例记录；
3. 复测：日志相关 CPU/IO 开销 ↓。

### 8. 线程池 / 协程池争抢

**通俗解释**：窗口太少导致排队，或者窗口里有人办慢业务堵住后面的人。

**为什么 Agent 需要解决它**：典型特征是"CPU 不高但吞吐上不去"，容易让团队误判方向；根因是配置或任务阻塞，Agent 能从队列/等待指标直接判断。

**具体解决方案**：
1. 看池队列长度、任务等待时间；
2. 判断根因：
   - **池太小** → 调大（如线程数 10→50）；
   - **任务阻塞** → 把慢任务/阻塞调用移出主池，快慢任务分池隔离；并追问"在等什么"——阻塞的根因可能是慢查询（问题 1）或下游慢调用（问题 6）；
3. 复测：队列等待时间 ↓、吞吐 ↑。

### 9. 配置 / 参数回退

**通俗解释**：本来水龙头开得好好的，某次改动手滑调小了，服务就变慢了。

**为什么 Agent 需要解决它**：这是"性能回退"最典型、最可自动化的场景——不是代码 bug，而是某个变更改小了参数；人工很难记得改过什么，Agent 靠配置审计 + 指标突变关联能秒级定位。

**具体解决方案**：
1. 发现指标在某个时间点突变（p99 上升、QPS 下降）；
2. 对比配置变更记录，找出同时间被改小的参数（连接池大小、线程数、超时、缓存大小）；
3. 恢复原值，并提示人工确认"不是有意的调优"；
4. 复测：指标回落到基线。

## 二、Agent 应具备的模块化功能

模块按"感知 → 诊断 → 处方 → 复测"四层划分，每个模块有单一职责、明确的输入输出。Agent 主控器（Orchestrator）按问题类型编排调用。

### 感知层（读数据）

| 模块 | 职责 | 输入 → 输出 |
|---|---|---|
| M1 指标采集器 MetricsCollector | 拉取 CPU/内存/QPS/延迟/错误率/池水位等时序指标 | 指标源+时间范围 → 结构化指标序列 |
| M2 基线管理器 BaselineManager | 存基线快照、算当前 vs 基线偏差、阈值判定触发告警 | 指标序列+基线 → 回归告警（哪个指标、变化幅度） |
| M3 慢查询解析器 SlowQueryParser | 解析慢查询日志为结构化数据 | 慢查询日志 → SQL、耗时、扫描行数、时间 |
| M4 Trace 分析器 TraceAnalyzer | 聚合相似 span/查询、算耗时占比、识别串行/并行、建连占比 | trace 数据 → 聚合结论 |
| M5 日志检索器 LogSearcher | 按关键词/模式检索日志 | 检索条件 → 命中日志 |
| M6 配置审计器 ConfigAuditor | 记录配置历史、diff 变更 | 配置源 → 变更清单 |
| M7 代码分析器 CodeAnalyzer | 定位 SQL/调用点在源码位置 + 识别反模式（循环内 query、new 连接、同步日志） | 符号/SQL/模式 → 代码位置与片段 |

### 诊断层（找根因）

| 模块 | 职责 | 输入 → 输出 |
|---|---|---|
| M8 执行计划分析器 ExplainAnalyzer | 对 SQL 跑 EXPLAIN，判断访问方式（`type=ALL/index/range/ref`）、索引命中（`key`）、扫描行数（`rows`），定位"扫描过多"的根因 | SQL → 执行计划结论 |
| M9 根因分类器 RootCauseClassifier | 把症状归类到问题类型/根因分支 | 症状证据 → 根因 + 置信度 |

### 处方层（给方案）

| 模块 | 职责 | 输入 → 输出 |
|---|---|---|
| M10 优化模板库 RecipeLibrary | 存每种问题的可执行优化模板（加索引 SQL、keyset 改造、异步日志配置、连接池参数…） | 问题类型+定位结果 → 具体改动建议 |
| M11 建议生成器 SuggestionGenerator | 组装成带风险提示、可直接落地的方案 | 模板+上下文 → 最终建议 |

### 复测层（验证）

| 模块 | 职责 | 输入 → 输出 |
|---|---|---|
| M12 复测执行器 RetestRunner | 优化后重新采集指标、与基线对比、算改善幅度、生成报告 | 优化前/后指标 → 复测报告 |

> **M0 编排器 Orchestrator**（隐含主控）：根据识别出的问题类型，按"调用链"依次调用上述模块，串起检测 → 定位 → 建议 → 复测全流程。

## 三、解决方案如何通过调用模块实现

每个问题的"解决方案"不是一段专属代码，而是**一条模块调用链（recipe）**。下表给出 9 个问题各自的调用链：

| 问题 | 模块调用链 |
|---|---|
| 1 慢查询/全表扫描 | M1(发现延迟↑) → M2(判定回退) → M3(拿慢 SQL) → M8(EXPLAIN 判访问方式/扫描行数) → M7(定位代码) → M10(加索引/改写模板) → M11(给建议) → M12(复测) |
| 2 N+1 查询 | M1 → M4(聚合同构小查询 + 证明随主对象数增长) → M7(定位循环内 query 触发代码) → M10(批量/预加载模板) → M11 → M12 |
| 3 连接池耗尽 | M1(池活跃/等待) → M5(查 timeout 日志) → M9(分类：泄漏/池小/慢查询) → M7(定位泄漏点) → M10(修释放/调池模板) → M11 → M12 |
| 4 深分页 | M3(发现大 OFFSET) → M8(确认代价) → M10(keyset 改造模板) → M11 → M12 |
| 5 响应体过大 | M1(响应大小/传输耗时) → M7(定位大响应接口) → M10(压缩/裁剪/分页模板) → M11 → M12 |
| 6 每请求新建连接 | M4(建连耗时占比) → M7(识别 new 连接反模式) → M10(连接池/keep-alive 模板) → M11 → M12 |
| 7 同步日志过多 | M1/M5(日志吞吐/写耗时) → M7(定位高频日志点) → M10(异步/降级/采样模板) → M11 → M12 |
| 8 线程池争抢 | M1(队列长度/等待) → M9(分类：池小/阻塞) → M10(调池/隔离模板) → M11 → M12 |
| 9 配置回退 | M1(指标突变) → M2(与基线对比确认回退) → M6(配置 diff 定位被改参数) → M10(恢复模板) → M11 → M12 |

### 检测判据的两条原则

- **提示性 vs 确证性信号**：提示性信号（`Rows_examined` 大、同构 SQL 多、指标突变）用来缩小范围，不能直接下结论；确证性信号（`EXPLAIN` 的 `type/key`、SQL 文本的 `OFFSET`、查询次数随集合大小增长、配置 diff）才用来定案。
- **诊断输出是"问题列表"而非单个结论**：一条 SQL 可能同时命中多个问题（如全表扫描 + 深分页），检出靠各自的确证信号一次扫完；定责与修复顺序靠迭代复测分层暴露。

### 模块复用的好处

- **同一个模块被多个问题复用**：M7（代码分析器）、M10（优化模板库）、M12（复测执行器）几乎每个问题都用到——新增一个问题，只需新增一条调用链和少量模板，不必重写定位/复测逻辑。
- **检测/定位/建议/复测解耦**：M1～M7 感知层通用；换一种问题只需换 M8～M9 的诊断逻辑；M10 的模板可持续沉淀，越用越准。
- **回退主线的统一入口**：M2（基线管理）是所有"回退类"问题的统一检测入口，符合"首版聚焦性能回退"的定位。
