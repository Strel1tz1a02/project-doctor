# 问题四 深度解析：深分页（大 OFFSET）

> 本文回答三件事：①深分页的**底层原因**；②如何通过**相关指标**诊断；③**为什么**这些指标能诊断（因果链）。

---

## 一、问题的本质

`OFFSET` 分页要求"**跳过前 M 行**"。数据库没有"直接跳到第 M 行"的捷径，只能**先扫描并丢弃前 M 行**，M 越大代价越高。

---

## 二、底层原因

### 2.1 根本机制：OFFSET 的代价是 O(M)

- `LIMIT N OFFSET M` 的语义是"取第 M+1 到 M+N 行"。
- 数据库无法定位"第 M 行在哪"，只能从头按顺序扫过前 M 行、把它们**读出来再丢弃**，直到第 M+1 行。
- **索引也救不了 OFFSET**：即使走索引，引擎仍要顺序遍历前 M 个索引项再丢弃。
- 因此 OFFSET 分页的代价与"要跳过的行数 M"**成正比**，而 M 随页码/业务数据增长——这就是"翻到后面越来越慢"的物理原因。

### 2.2 具体成因

| # | 原因 | 说明 |
|---|---|---|
| 1 | 业务用 OFFSET 做深分页 | 前端允许翻到几百上千页 |
| 2 | 数据持续增长 | 同样的页码，M 越来越大 |
| 3 | 未限制最大页 | 用户可以请求任意大的 OFFSET |

> 这是"数据规模增长导致的隐性退化"的典型：代码没变，数据多了，深页就慢了——属于性能回退的一种。

---

## 三、如何通过相关指标诊断

### 3.1 诊断指标清单

| 指标来源 | 指标 | 诊断信号 |
|---|---|---|
| **慢查询日志** | SQL 文本 | 含大 `OFFSET`（如 `LIMIT 20 OFFSET 100000`） |
| | `Rows_examined` | 很大（跳过的 M 行也计入） |
| | `Rows_sent` | 很小（只返回 N 行） |
| **应用指标** | 该 SQL 耗时 | 随页码（OFFSET）递增 |
| **EXPLAIN** | `rows` 估算 | 扫描行数大 |

### 3.2 诊断流程

```
① 现象：分页接口"翻到后面变慢"
        ↓
② 识别：慢查询日志里的 SQL 带大 OFFSET
        ↓
③ 确认：Rows_examined 大（≈M+N）而 Rows_sent 小（=N）
        ↓
④ 区分：SQL 有 LIMIT/OFFSET 关键字 → 深分页，而非全表扫描
        ↓
⑤ 修复：keyset 分页 / 限制最大页
```

### 3.3 具体例子

```sql
SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 100000;
```

慢查询日志：`Query_time: 2.1s, Rows_examined: 100020, Rows_sent: 20`。

诊断：`Rows_examined=100020`（跳过的 10 万行 + 返回的 20 行），`Rows_sent=20` → 扫描 10 万行只留 20 行，典型深分页。修复：改成 keyset `WHERE id > 上次最大id ORDER BY id LIMIT 20`，耗时从 2.1s 降到毫秒级。

> **与全表扫描共存时**：若同一 SQL 既有无索引的谓词（如 `LIKE '%x%'`）又带大 `OFFSET`，全表扫描的 `Rows_examined`（≈整表行数）会**淹没** OFFSET 的 M 行——此时 `type=ALL`，两个问题同时存在。需**迭代诊断**：先修全表扫描（消除 `type=ALL`）→ 复测 → 全表扫描的代价去掉后，OFFSET 的剩余成本才可量化，再决定是否改 keyset。

---

## 四、为什么这些指标能诊断出该问题（因果链）

### 4.1 为什么 `Rows_examined` 大而 `Rows_sent` 小

OFFSET 要求引擎"扫描并丢弃前 M 行"，被丢弃的行**同样计入 `Rows_examined`**。走索引时（`type=index`）深分页的 `Rows_examined ≈ M + N`，而 `Rows_sent = N`——比值悬殊正是"读了很多、只留一点"的量化证据。（若排序列无索引、`type=ALL`，则 `Rows_examined ≈ 整表行数`，此时全表扫描是主导、OFFSET 被淹没，见 4.3。）

### 4.2 为什么耗时随页码递增

因为 OFFSET 的代价是 O(M)，M 随页码线性增长，所以同一 SQL 的耗时随 OFFSET 增大**线性上升**。"越翻越慢"的曲线，就是 O(M) 代价的直观体现。

### 4.3 为什么能与全表扫描（问题一）区分

两者 `Rows_examined` 都大，但**区分不能靠 `Rows_examined`，也不能靠 `type`**——因为深分页本身也可能是 `type=ALL`（排序列无索引、或谓词无法用索引时）。

- **全表扫描**：判据是 EXPLAIN `type=ALL`（访问路径扫整表）；
- **深分页**：判据是 SQL 文本含大 `OFFSET`（与访问路径无关）。

两者**正交、可叠加**：深分页只由 `OFFSET` 大小决定，全表扫描只由 `type=ALL` 决定，各自独立。但要澄清一点：`type=index`（全索引扫描）、`type=range`（范围扫描）本身也是"扫描"访问方式，索引/范围巨大时同样是"扫描过多"问题——所以"`type=index/range` 且带大 `OFFSET`"只能断定"至少有深分页"，不能断定"没有扫描问题"。正确做法始终是**分别用各自判据**，而不是用 `type` 去二选一。

### 4.4 为什么索引救不了 OFFSET

索引能加速"按值定位"，但 OFFSET 需要的是"按位置跳过"。即使走索引，引擎仍要顺序遍历前 M 个索引项。所以深分页的修复不是"加索引"，而是**换掉 OFFSET 语义本身**（keyset）——这也是它必须单独作为一类问题的原因。

