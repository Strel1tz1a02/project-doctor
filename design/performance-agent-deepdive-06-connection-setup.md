# 问题六 深度解析：每请求新建连接

> 本文回答三件事：①每请求新建连接的**底层原因**；②如何通过**相关指标**诊断；③**为什么**这些指标能诊断（因果链）。

---

## 一、问题的本质

每次调用下游服务都**重新建立 TCP/TLS 连接**，而不是复用已有连接，把"握手"这个固定成本在每次请求上重复支付。

---

## 二、底层原因

### 2.1 根本机制：连接的建立是"一次性固定成本"

- 一次 HTTP 请求要经过：**TCP 三次握手**（1 RTT）+ **TLS 握手**（1～2 RTT，即使 TLS 1.3 也至少 1 RTT）+ 业务请求/响应。
- 握手往返是**固定开销**，与"这次请求传多少数据"无关。
- **复用连接**（keep-alive / 连接池）能把握手成本摊薄到多次请求；**每请求新建**则让每次请求都完整付一遍握手成本。

### 2.2 具体成因

| # | 原因 | 说明 |
|---|---|---|
| 1 | 每次调用都 new 客户端 | 客户端对象用完即弃，连接随之关闭 |
| 2 | 未启用 keep-alive | 服务端/客户端强制每次关闭连接 |
| 3 | 未配置连接池 | 没有连接复用机制 |

> 微服务/外部依赖越多，这个开销越被**成倍放大**——每个下游都多付一次握手。

---

## 三、如何通过相关指标诊断

### 3.1 诊断指标清单

| 指标来源 | 指标 | 诊断信号 |
|---|---|---|
| **trace** | 建连耗时（TCP connect / TLS handshake）占比 | 占总耗时比例高 |
| | 请求处理耗时 | 很短（业务本身不慢） |
| **连接指标** | 连接创建/销毁频率（churn） | 频繁新建/关闭，连接数锯齿状波动 |
| **应用指标** | 平均延迟 | 偏高，但服务端处理时间正常 |

### 3.2 诊断流程

```
① 现象：接口平均延迟偏高，但服务端处理时间短
        ↓
② 拆分：trace 里把"建连耗时"和"请求处理耗时"分开
        ↓
③ 确认：建连耗时占比高
        ↓
④ 定位：代码里找每次调用都 new 客户端 / 未复用的位置
        ↓
⑤ 修复：连接池 / keep-alive / 复用客户端实例
```

### 3.3 具体例子

服务 A 每次调用服务 B 都 `new HttpClient()` 并发起请求，用完即弃。每次请求额外支付 TCP+TLS 握手约 100ms（跨地域），而业务处理只要 20ms。

诊断：trace 显示建连耗时 100ms、请求处理 20ms，建连占比 83%。修复：改用全局复用的 `HttpClient` + keep-alive，握手成本被摊薄到接近 0。

---

## 四、为什么这些指标能诊断出该问题（因果链）

### 4.1 为什么"建连耗时占比高"能定位

把总延迟拆成"握手"和"业务"两段，若握手占比高，说明时间花在**连接的建立**而非业务处理。这个"两段拆分"直接暴露了"钱花在了哪"，是指向连接建立问题的核心证据。

### 4.2 为什么"服务端处理快、整体却慢"是特征

业务本身不慢，慢在业务之前的"握手前摇"。这个**断层**（处理时间与总延迟之间的差值）恰好等于连接建立的开销，差值越大、越指向建连问题。

### 4.3 为什么连接 churn 能暴露未复用

连接复用表现为"少数长连接反复使用"，连接数曲线平稳；每请求建连表现为"连接频繁新建/销毁"，连接数呈**锯齿状高频波动**。这条锯齿曲线是"每请求建连"的指纹。

### 4.4 为什么它在微服务架构下更值得诊断

单机单体里，建连开销可能只占个位数毫秒，容易被忽略；微服务/多下游下，握手成本按下游数量**叠加**，还可能叠加跨地域 RTT。所以它的价值随架构复杂度上升——这正是 Agent 要从 trace 里"自动算占比"而非靠人肉观察的原因。

## 五、对 Agent 模块的落点

```

  → M7 代码分析器（识别"每次 new 客户端 / 未复用"反模式）
  → M10 优化模板库（连接池 / keep-alive / 复用实例模板）
  → M12 复测执行器（建连耗时占比↓、平均延迟↓）
```
