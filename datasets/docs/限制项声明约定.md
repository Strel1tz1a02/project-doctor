# 限制项声明约定（给数据方）

> 本文是开发者 B（诊断层）写给数据方的建议，解决「边界/失败用例的 `limitation_declared` 硬闸门在隔离运行的 SUT 下不可达」的问题。它是约定，不是代码改动。**建议数据方按第 4 节改写 `case.json` 的 `expected.limitations_required`，并按第 7 节同步黄金样例。**

## 1. 结论先行

`case-02` 与 `case-05` 的 `limitation_declared` 判不过，根因不在诊断 Agent 偷懒，而在 `limitations_required` 的原文内嵌了隔离运行下 SUT **不可能知道**的信息：

- 缺陷 ID（`d2`/`d3`/`d4`/`d5`）——评测方资产，防泄漏，SUT 看不到；
- 个案字段（`email`、`status`、`PAID`）——随样例变化，通用诊断层不会逐字复现；
- 模板前缀「必须声明」——与后续中文粘连成一个长词元，永远匹配不上。

这三类词在 `text_covers` 里都算「必须覆盖的显著词元」，把覆盖率拖到 0.6 阈值以下。**去掉它们、改用通用机制措辞后，SUT 的确定性输出即可稳定达标**（第 6 节附实测覆盖率）。

## 2. 判定机制（为什么原文不可达）

`datasets/evaluation/contract.py` 的 `text_covers(declared, required)` 分两级：

1. 规范化子串命中 → 直接通过；
2. 否则按显著词元覆盖率 ≥ 0.6 判定。词元 = `[a-z0-9_]+` 或**连续中文串**（`[一-鿿]+`），过滤 len<2 与停用词（的/了/与/和/或/是/在/对/为）。

两个关键后果：

- `d2` 是 len=2 的合法词元，**计 1 个覆盖点**；`N+1` 被拆成 `n`/`1`（len=1）不计数。
- 连续中文串是一个原子词元，只能整串子串命中。「必须声明」和后面的中文连写（如「必须声明索引收益依赖被查询的…」）会融成**一个 15 字长词元**，SUT 不可能整串复现。

### 工作示例：case-02 #1 原文

原文：`必须声明 d2（email 前导通配符）、d3（N+1）、d4（COUNT）、d5（深分页）未能在单变量索引实验下证实`

显著词元 10 个：`必须声明`、`d2`、`email`、`前导通配符`、`d3`、`d4`、`count`、`d5`、`深分页`、`未能在单变量索引实验下证实`。

其中 `必须声明`/`d2`/`d3`/`d4`/`d5` 5 个 SUT 不可知；SUT 最多命中其余 5 个 = 50% < 60%，**不可达**。

去掉 ID 后剩 6 词元，SUT 命中 5 个 = 83%；再连「必须声明」一起去掉（见第 6 节），更稳。

## 3. SUT 侧已经做了什么（背景）

诊断层的限制项是**纯确定性文本**，来源固定（`check_slow_query` 的 `reasons` + `scope_limitations` + 两条固定说明），模型无法注入个案措辞。本轮已做了两处增强：

- **P0 选择性守卫**：EXPLAIN `filtered`（0–100）出现低选择性（≥50%）时，`verified` 降为 `lead` 并附倾斜限制——修掉 case-05 的误验证（全局零容忍）。
- **P1 限制项增强**：LIKE 点名具体列、合并「…等候选根因未能在单变量索引实验下证实」、深分页措辞对齐。

因此 SUT 能产出的是**通用机制短语**（见第 5 节词表），而非「d2/d3」或「status/PAID」这类个案字面量。

## 4. 约定（4 条硬规则）

写 `expected.limitations_required` 的每一项时：

1. **不含缺陷 ID**：`d2`/`d3`/… 一律去掉；「哪个缺陷」由 `root_cause_ids` / `defects` 承载，限制项只描述「什么机制未被证实」。
2. **不含个案字面量**：`email`/`status`/`PAID` 这类随样例变的列名/取值，换成通用词（`前导通配符`、`过滤值`、`高占比取值`）。
3. **不加「必须声明」模板前缀**：字段名 `limitations_required` 已隐含「必须声明」，前缀会与后续中文粘连成不可达长词元。
4. **用短片段、复用第 5 节词表的短语**：长连写中文串是原子词元，写短、按标点断开，命中率才稳。

一句话：**`limitations_required` 描述「什么机制/范围未证实」，用通用词；不描述「怎么措辞」「哪个编号」「哪张表哪个值」。**

## 5. SUT 确定性限制词表（写 required 时可直接复用）

`scope_limitations`（`features/diagnosis/query_scope.py`）按 SQL 形状产出：

| 触发 | 短语 |
| --- | --- |
| 固定 | 结论仅适用于本次请求参数、数据规模、过滤值和数据分布；分布变化会改变索引收益 |
| 固定 | 索引收益依赖被查询的过滤值：高占比取值下优化器可能仍走全表扫描，收益不稳定 |
| `COUNT(` | COUNT(*) 的耗时贡献未通过单独删除或改写计数查询的实验证实 |
| `LIKE` | {列} 前导通配符 LIKE '%…%' 可能限制普通索引收益（{列} 由 SQL 抽取，如 email） |
| 模板数>2 | 多条查询可能涉及 N+1，但本次未单独改变调用次数，不能证实 N+1 根因 |
| `LIMIT` | 深分页未通过改变 offset 或分页方式的单变量实验单独证实；分页与 COUNT 的耗时结论依赖数据规模与 offset 大小 |
| ≥2 个候选 | …等候选根因未能在单变量索引实验下证实 |

另有固定两条（`check_slow_query`）：`不自动宣称缺索引是所有慢查询的原因，不推断线上频率或业务 SLA`、`测量策略：…`；低选择性降级时还含 `…过滤选择性过低（filtered ≥ 50%），高占比取值下优化器可能仍走全表扫描…`。

## 8. 自检脚本（数据方写完随手验证公平性）

```bash
uv run python - <<'EOF'
import sys
from pathlib import Path
sys.path.insert(0, "datasets/evaluation")
from contract import text_covers
from project_doctor.features.diagnosis.query_scope import scope_limitations

# 把该样例实际会出现的归一化 SQL 列在这里（与症状/缺陷一致）
templates = [
    "SELECT * FROM orders WHERE email LIKE '%x%' AND status = 'PAID' ORDER BY created_at DESC LIMIT 20",
    "SELECT COUNT(*) FROM orders WHERE status = 'PAID'",
    "SELECT * FROM users WHERE id = ?",
]
declared = "\n".join(scope_limitations(templates))

required = [
    "email 前导通配符、N+1、COUNT、深分页未能在单变量索引实验下证实",
    "深分页/COUNT 的耗时结论依赖数据规模与 offset 大小",
]
for item in required:
    print("PASS" if text_covers(declared, item) else "FAIL", "|", item)
EOF
```

凡新增边界/失败用例，写完 `limitations_required` 后都跑一遍此脚本，确保每项 ≥0.6；否则该用例的 `limitation_declared` 会成为「隔离 SUT 必然判不过」的无效闸门。
