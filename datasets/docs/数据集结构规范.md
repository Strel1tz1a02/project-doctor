# 数据集结构规范

本规范定义 `Datasets/` 下每个数据单元的目录组织与元数据约定。数据单元同时承担两个角色：它既是诊断 Agent 的输入（症状 + 可运行项目），也是评估时 ground truth 的唯一来源。

一个数据单元 = 一个可独立构建运行的后端项目 + 一张记录「已知缺陷与期望结论」的问题卡。

## 目录结构

```
datasets/                         # 并入 project-doctor 仓库的只读金标准目录
├─ README.md                      # 数据单元索引，便于导航
├─ docs/
│  ├─ 数据集结构规范.md            # 本文件
│  └─ Agent评估方法.md
├─ _schema/
│  └─ case.schema.json            # 问题卡的 JSON Schema
├─ _template/                     # 新增用例模板 + 自检清单（保留目录，非数据单元）
│  ├─ case.json                   #   一张完全合规的问题卡样板
│  ├─ project/README.md           #   project/ 标准布局与硬约束
│  └─ README.md                   #   三、新增用例自检清单
└─ <case-id>/                     # 一个数据单元
   ├─ case.json                   # 问题卡（ground truth）
   ├─ README.md                   # 用例说明，面向组员
   └─ project/                    # 被测项目，可独立构建与运行
```

`docs/`、`_schema/`、`_template/` 以及任何以 `_` 开头的名字都是保留目录/文件，不被视为数据单元；
`tools/validate_cases.py`、`tools/isolation_guard.py` 与 `tools/guard_sut_separation.py` 在自动发现时会一致地跳过它们。

新增用例请从 `_template/` 起手：复制其 `case.json` 与一份现成 `project/` 基线，改完变量后
按 `_template/README.md` 的**自检清单**逐项确认，跑通 `validate_cases.py` + `isolation_guard.py` 再提交。

> **归属与只读性**：本数据集以「方案 B」并入 `project-doctor` 仓库的 `datasets/` 子目录。目录内的
> `case.json`、`README.md`、`docs/`、`_schema/` 均为**只读金标准**，被测 Agent 与 SUT 源码
> （`src/project_doctor`）一律不得引用；该约束由 `tools/guard_sut_separation.py` 在 CI 中强制
> （见 `tools/README.md` 的 CI 章节）。

### 命名约定

`<case-id>` 采用 `case-<两位序号>-<问题类型>-<变体>`，全小写、以连字符分隔。问题类型取自 `problem_kind` 字段；变体用于区分同一问题类型下的不同用例，例如：

- `case-01-slow-query-fullscan` —— 正常用例，缺复合索引导致全表扫描
- `case-02-slow-query-composite` —— 边界用例，同类缺陷叠加多个干扰项，仅主缺陷可证实
- `case-03-slow-query-unreproducible` —— 失败用例，观测证据缺失、无可证实缺陷

变体名应概括「本用例与同类型其他用例的差异」，如 `fullscan` / `composite` / `undersized` / `skewed-status`，避免使用 `variant1`、`test` 等无信息量的词。

### problem_kind 取值与覆盖现状

`problem_kind` 的取值域对齐 `project-doctor` 设计文档划定的 **9 类性能问题**（见 `design/performance-agent-modular-design.md`）。枚举一次性预留全部 9 类，避免后续新增问题类型时反复改动 schema；但**当前仅有 3 类以用例落地**，其余 6 类为预留取值（**待补**，暂无对应用例卡片）。

| # | `problem_kind` | 中文含义 | 覆盖现状 |
| --- | --- | --- | --- |
| 1 | `slow_query` | 慢查询 / 全表扫描 | 已有用例：`case-01`~`case-06` |
| 2 | `n_plus_one` | N+1 查询 | 已有用例：`case-07` |
| 3 | `connection_pool` | 连接池耗尽 / 泄漏 | **待补** |
| 4 | `deep_pagination` | 深分页（大 OFFSET） | 已有用例：`case-08` |
| 5 | `large_response` | 响应体过大 | **待补** |
| 6 | `connection_setup` | 每请求新建连接 | **待补** |
| 7 | `excessive_logging` | 同步日志过多 | **待补** |
| 8 | `thread_pool` | 线程池 / 协程池争抢 | **待补** |
| 9 | `config_regression` | 配置 / 参数回退 | **待补** |

> `problem_kind` 取值即命名里的「问题类型」段（如 `case-07-n-plus-one-order-user` 对应 `n_plus_one`）。
>
> 预留 ≠ 可立即产出 `verified`：Agent 侧 `ProblemKind` 契约尚未覆盖这 6 类，新增用例（若编写）的期望结论仍应标注为 `lead` / `unclassified` 并在 `evaluation.notes` 写明「等待 Agent 支持」，详见下文「与 project-doctor 契约的映射」的现状提示。

### 关键约束：答案隔离

`case.json` 记录了期望结论，绝不能让被测的诊断模型读到。评估运行时只把 `case-<id>/project/` 暴露给 Agent，`case.json`、`README.md`（若含答案）与 `docs/` 均不可见。被测项目内部也不能通过符号链接、构建脚本或初始化数据引用这些文件。

这一点写在目录结构层面，而不是靠运行时的自觉：元数据与项目实物物理分离，是防止答案泄漏的第一道防线。

## 用例三分类

每个数据单元必须归入以下一类，它直接决定评估时的期望结论与判定标准（详见《Agent 评估方法》）。

| `case_type` | 设计意图 | 期望结论 |
| --- | --- | --- |
| `normal` | 单一主缺陷，证据链完整，可通过单变量实验证实 | `verified` |
| `boundary` | 症状具误导性，或结论依赖数据规模/缓存/数据分布等条件 | `lead`，或缺 `verified` 但须声明适用范围 |
| `failure` | 环境不可用、证据缺失、测量波动过大，根因无法被证实 | `unclassified`，并报告「证据不足」 |

三类用例对应赛事规则要求的正常、边界、失败样例，一个完整的数据集应同时覆盖三类。

## 问题卡 case.json

### 顶层字段

| 字段 | 必填 | 类型 | 说明 |
| --- | --- | --- | --- |
| `case_id` | 是 | string | 与目录名一致 |
| `schema_version` | 是 | string | 固定 `"0.1"`，随规范升级 |
| `title` | 是 | string | 一句话描述用例 |
| `case_type` | 是 | enum | `normal` / `boundary` / `failure` |
| `difficulty` | 是 | enum | `easy` / `medium` / `hard` |
| `problem_kind` | 是 | enum | 9 类问题类型之一，取值与覆盖现状见下文「[problem_kind 取值与覆盖现状](#problem_kind-取值与覆盖现状)」 |
| `stack` | 是 | object | 语言、框架、数据库及版本 |
| `symptom` | 是 | object | 给 Agent 看的表象信息（不含根因） |
| `runtime` | 是 | object | 启动方式、健康检查、目标接口、负载参数 |
| `dataset_profile` | 是 | object | 数据规模、初始化方式、缓存/预热状态 |
| `defects` | 是 | array | 注入缺陷清单，至少一个 `role=primary` |
| `expected` | 是 | object | 期望 Agent 输出的结论与命中项 |
| `evaluation` | 是 | object | 该用例适用的检查项、权重与超时 |
| `provenance` | 否 | object | 作者、创建时间、来源、许可 |

### 缺陷对象 defects[]

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `defect_id` | 是 | 用例内唯一，建议 `d1`、`d2` |
| `role` | 是 | `primary`（主缺陷）/ `secondary`（次要缺陷）/ `decoy`（干扰项，本不该被判定为根因） |
| `kind` | 是 | 机制标签，如 `full_table_scan`、`missing_composite_index`、`n_plus_one`、`deep_offset` |
| `mechanism` | 是 | 一句话说明底层机制 |
| `code_locations` | 是 | 数组，每项 `{path, line, symbol}`，`path` 相对 `project/` |
| `expected_fix` | 是 | 预期修复（加索引 / 改写 SQL / 改分页方式） |
| `expected_status` | 是 | 该缺陷期望被给出的置信度：`verified` / `lead` / `unclassified` |

`primary` 缺陷是单变量对照实验的作用对象。一个用例只应有一个 `primary`，其余缺陷要么作为被排除的干扰（`decoy`），要么作为不改动变量即可确认的附带发现（`secondary`）。

### 期望对象 expected

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `decision` | 是 | 整体期望结论：`verified` / `lead` / `unclassified` |
| `root_cause_ids` | 是 | 期望命中的 `defect_id` 列表 |
| `code_locations` | 是 | 期望被定位到的代码位置，格式同缺陷对象 |
| `excluded_explanations` | 否 | 期望被主动排除的干扰解释，对齐 `Finding.excluded_explanations` |
| `improvement` | 否 | 期望改善：`{metric, min_improvement_percent, tolerance}` |
| `limitations_required` | 否 | 边界/失败用例必须声明的限制项，缺失即判不合格 |

### 与 project-doctor 契约的映射

评估器只读取 Agent 的产出契约，因此 `case.json` 的字段需要能一一对应上。映射关系如下：

| case.json | Agent 产出 | 说明 |
| --- | --- | --- |
| `expected.decision` | `Finding.status` | 取值域 `verified` / `lead` / `refuted` / `unclassified` |
| `problem_kind=slow_query` | `Finding.kind` | `Finding.kind` 的类型是 `ProblemKind`，当前仅支持 `slow_query` 与 `unclassified`；我们问题卡的 `problem_kind` 已预留 9 类，二者取值域暂不对齐 |
| `defects[].code_locations` | `Finding.code_locations` | 逐条比对 `path` 与 `line`；比对只用这两个字段 |
| `expected.excluded_explanations` | `Finding.excluded_explanations` | 我方为字符串列表，Agent 侧为对象列表，按对象内的 `explanation` 比对 |
| `expected.improvement` | `Recommendation.measured_gain_percent` | 该值经 `no_unmeasured_gain` 校验，仅在 `validation_status=retested` 时非空、才可信 |
| — | `Impact.method` | 取值 `intervention` / `sql_time_estimate` / `unmeasured`，`intervention` 为唯一可信的影响度量方式 |
| — | `Finding.limitations` | 边界/失败用例要求的限制项，对应 `expected.limitations_required` |
| — | `Observation.business_valid` | 业务断言结果，是 `correctness_preserved` 的数据来源 |

对齐真实契约时需要注意几处细节：

- `Finding.code_locations` 的元素是 `CodeLocation`，真实字段为 `commit`、`path`、`line`、`association_evidence_ids`，**不含 `symbol`**。`symbol` 只是问题卡里便于人阅读的补充信息，评估不依赖它；`association_evidence_ids` 为必填（`min_length=1`），即每个被定位的代码位置都必须带上佐证。
- `Finding.excluded_explanations` 的元素是 `ExcludedExplanation` 对象 `{explanation, evidence_ids}`，不是纯字符串。问题卡里写名称即可，评估时取对象中的 `explanation` 做比对。
- 证据类指标依据的是 `SqlCall` 的实测字段 `duration_ms`、`rows_examined`、`rows_returned`、`lock_wait_ms`。这些字段的校验规则要求：有值就必须来源为 `actual`，估算值只能出现在执行计划里——因此问题卡的期望值应是可实测的量。
- `dataset_profile` 与 Agent 契约中的 `DatasetProfile`（`models/dataset.py`）同名但语义不同：前者描述用例自带的测试数据规模与缓存状态，后者描述 Agent 被授权使用的数据集来源（`authorized_sample` / `project_seed` / `synthetic` 等）。两者不要混用同一个字段。

> 现状提示：`project_doctor.models.common.ProblemKind` 目前只有 `slow_query` 与 `unclassified`；与之相对，我们问题卡的 `problem_kind` 已按设计文档预留 **9 类**（其中 `connection_pool` / `large_response` / `connection_setup` / `excessive_logging` / `thread_pool` / `config_regression` 为**待补**，见「problem_kind 取值与覆盖现状」）。N+1、深分页以及 6 类待补问题现在就可以按本规范编写与归档，但在 Agent 扩展 `ProblemKind` 之前，这些用例的期望结论应标注为 `unclassified` 或 `lead`，并在 `evaluation.notes` 里写明「等待 Agent 支持」。与之对应，`Finding` 的 `verified_requires_structural_evidence` 校验也要求 `kind == "slow_query"`，所以在 Agent 扩展前，非 `slow_query` 类用例不可能产出 `verified`。

### 元数据的规范表述

为了让评审与跨用例对比保持同一口径，`difficulty`、`provenance`、`evaluation.notes` 与数据规模描述按本节约定填写。

#### difficulty 难度分级

`difficulty` 不凭主观印象，而由四项客观特征决定（取其中最强的一项）：

| 取值 | 判定特征 | 现有用例 |
| --- | --- | --- |
| `easy` | 单一主缺陷，无干扰项或干扰项显而易见；一次单变量实验即可闭环；数据规模充足、结论不受条件约束 | `case-01`、`case-04` |
| `medium` | 主缺陷可证实，但需处理少数干扰项；或结论依赖数据分布 / 规模而必须声明限制；或失败用例需抑制「强行下结论」；或问题类型尚未被 Agent 支持而只能给 `lead` | `case-03`、`case-05`、`case-06`、`case-07`、`case-08` |
| `hard` | 多缺陷叠加、症状具强误导性，存在多个看似合理的竞争假设，须逐一设计实验排除 | `case-02` |

判断特征：缺陷数量与角色分布、是否需要排除 `decoy`、结论是否受条件约束、证据链长度。

#### provenance 溯源

| 字段 | 约定 |
| --- | --- |
| `author` | 默认统一为 `dataset-team`；个人贡献另在用例级 `README.md` 记录 |
| `created_at` | 问题卡定稿日期，ISO 格式 `YYYY-MM-DD` |
| `source` | 枚举式取值：`handcrafted`（手工设计与实现，当前全部用例）/ `adapted`（改编自真实工单或开源项目）/ `captured`（自真实环境采集） |
| `license` | 默认 `internal` |

#### evaluation.notes 必写内容

每张问题卡都应填写 `evaluation.notes`，至少覆盖以下四点：

1. **用例类型与设计意图**——本用例用于检验 Agent 的哪种行为；
2. **可证实性判定**——`primary` 缺陷能否由单变量实验（`baseline` 对照 `candidate_index`）证实；不能证实的要写明原因（分布倾斜 / 规模不足 / 无可复现缺陷）；
3. **干扰项处理**——`decoy` / `secondary` 为何不应被判为根因；
4. **待支持标注**——若涉及 Agent 尚未支持的问题类型（N+1 / 深分页，以及上文 6 类待补问题），写明「等待 Agent 支持」。

#### 数据规模表述

- `dataset_profile.row_counts` 必须与 `project/` 内初始化逻辑（如 `DataInitRunner`）**实际生成的行数一致**；
- `dataset_profile.init` 需说明初始化方式、随机种子与关键分布（如「`status` 按业务权重倾斜：PAID 8/10」）；
- 边界 / 失败用例的**小数据量、倾斜分布**必须如实填写——数据规模本身即用例的设计变量（如 `case-06` 仅 300 条订单，正是其「不可证实」的成因），不得为「看起来正常」而虚报规模。

## 编写一个用例的验收要求

一张问题卡从草稿转正，需要同时满足以下几点，否则不予收录：

可复现。同一负载下重复至少 3 次，指标的相对波动不超过 **25%**（**验收口径**，对应 Agent 的 `MeasurementPolicy`），慢查询耗时与对照组之间可区分。注意评测器在运行期另有一个更严的 **10% 运行 / 复测口径**，用于判定「某一次运行当场采集到的基线是否可复现」，两者各自命名、不得混用，详见《Agent 评估方法》第三步与 `evaluation/run_eval.py` 中的 `ACCEPTANCE_DISPERSION_THRESHOLD` / `RETEST_DISPERSION_THRESHOLD`。

单变量可控。`primary` 缺陷能够通过唯一变量（`baseline` 对照 `candidate_index`）区分出来；若一个改动同时牵动多个缺陷，应拆分为多个用例。

代码定位确定。每个缺陷都有唯一的 `path:line`，且在目标版本 commit 上稳定。

正确性可断言。提供业务断言（如返回行数、关键字段），用于判断修复是否破坏了功能。

答案隔离。`project/` 不引用 `case.json`、`docs/`、`_schema/`，构建与初始化过程中也不读取。

环境可恢复。对数据库、索引、配置的任何改动都能回滚，附带回滚后的校验方式。

## 演进约定

`schema_version` 采用「主版本.次版本」。新增可选字段递增次版本，破坏性变更递增主版本，并同步更新 `_schema/case.schema.json`。

组合缺陷项目应作为 `boundary` 用例归档：主缺陷仍标 `primary`，其余标 `secondary` 或 `decoy`，并在 `expected` 中说明各缺陷的判定顺序与预期结论。多个缺陷混在一起、无法单变量区分的情况，不应作为 `normal` 用例。
