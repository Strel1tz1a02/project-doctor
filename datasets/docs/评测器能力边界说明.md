# 评测器能力边界说明

> 面向读者：队长 / 组员（含负责被测 Agent、负责实验执行的同事）
> 目的：**一句话说清** —— 评测器是「判卷机」，不是「考场」。它**不会替你跑实验**。
> 适用版本：`datasets/`（方案 B，已并入 `project-doctor`）

---

## 0. 一句话结论

评测器（`datasets/evaluation/`）是一个**完整、可即用的判分器（judge）**：

> 只要你按约定交上一份**运行包（run bundle）**，它就能算出全部指标、硬闸门、总分与人类可读报告，且结论**可复现、可回溯**。

但它**不启动被测系统、不应用你的代码改动、不跑压测、不采集轨迹与制品**。
「把我改好的代码和原代码拿来跑一轮对照实验」这件事，属于**执行 / 采集侧**，**不在本数据集工程范围内**（团队硬边界：只做数据集与评价方法，绝不调用 SUT）。

---

## 1. 它「是」什么 / 它「不是」什么

| 维度 | 评测器**是**（已实现） | 评测器**不是**（未实现，且不在本工程范围） |
| --- | --- | --- |
| 角色 | 判分器 / 阅卷机 | 实验执行器 / 考场 |
| 输入 | 结构化**运行包** JSON | 原始代码 + 修改后代码（不会自己去取） |
| 动作 | 读运行包 → 计算指标 → 判闸门 → 聚合 → 出报告 | 启动服务、应用补丁、造压、跑基线、采集证据 |
| 是否触碰 SUT | **从不触碰**（纯数据计算，标准库实现） | 需要真正运行被测 Agent 与数据库 |
| 输出 | `report.json` + `report.md` | 原始测量数据（须由执行侧提供） |
| 谁来产输入 | 执行侧（跑实验的人 / 被测 Agent 的运行框架） | —— |

一句话：**判分链完整可用；「取修改后代码跑对照实验」的执行链未实现，也不属于本方交付。**

---

## 2. 已完整实现的判分链路（7 步）

入口：`python evaluation/run_eval.py --runs <运行包目录> --out <输出目录>`
编排实现见 `evaluation/run_eval.py` 的 `run(...)`，逐步骤如下：

1. **冻结评测器指纹**：对 `FROZEN_RELATIVE` 列出的 9 个评测器文件做哈希，写入报告 `manifest.evaluator_hash`，保证「结论可回溯到评测器版本」。
2. **加载用例**：扫描 `case-*/case.json`，按 `_schema/case.schema.json` 做结构校验（结构失败会列入报告的 `schema_validation.failed`）。
3. **读基线**：从运行包 `baseline.repeats_ms` 算基线统计与**可复现性**（验收口径 25%、复测口径 10%、最少 3 次）。
4. **装载运行包**：`EvalInput.from_raw(case, bundle["report"], trajectory=..., retest=..., artifacts=..., restore=..., cost=..., honesty_override=..., line_tolerance=...)`。
5. **自动评测**：`metrics.evaluate_case(...)` 计算四层指标（结论 / 证据 / 过程 / 成本），生成逐用例闸门。
6. **独立复测**：复测结论取自运行包 `retest` 字段（评测器不自己复测）。
7. **聚合 + 全局门槛**：`aggregate(...)` 汇总；全局硬门槛 **`false_verified` 次数必须为 0**（误验证率 = 0），输出 `report.json` 与 `report.md`。

> 说明：评测器自身也能「自检」——不带 `--runs` 运行时会用内置三份样例跑一遍闭环（`_self_check()`），证明判分逻辑自洽；这**不是**在跑任何真实实验。

## 3. 输入契约：运行包（run bundle）＝ 唯一的接口边界

运行包是一份 JSON，文件名必须是 `<case-id>.json`，放在 `--runs` 指向的目录下。
评测器读取的**全部**顶层键如下（未列出的键会被忽略）：

| 键 | 必需 | 类型 | 含义 / 由执行侧提供的内容 |
| --- | --- | --- | --- |
| `baseline` | 建议 | object | `repeats_ms: number[]`（原始代码基线重复测量）、`environment_fingerprint`。用于基线可复现性判定 |
| `report` | **必需** | object | Agent 的**诊断结论**：`task.status`、`findings[]`（`status` / `code_locations` / `evidence_refs` / `excluded_explanations` / `recommendation` / `evidence_flags`）、`observations`、`reason` |
| `trajectory` | 建议 | object | 过程证据：`required_steps_done`、`hypothesis_count`、`experiments_single_variable`、`records_retained`、`tool_calls` |
| `retest` | 建议 | object | 复测结果：`performed`、`improvement_percent`、`business_assertions_passed` |
| `artifacts` | 建议 | array | 制品证据：`ref`、`sha256_verified`、`readable` |
| `restore` | 建议 | object | 环境回滚：`rolled_back`、`verified` |
| `cost` | 建议 | object | 成本层：`wall_seconds`、`tool_calls`、`artifact_bytes` |
| `honesty_override` | 可选 | string | 人工覆盖 `honesty` 取值（`pass` / `partial` / `fail`） |
| `line_tolerance` | 可选 | number | 代码定位行号容差，缺省 5（`contract.DEFAULT_LINE_TOLERANCE`） |

- 键缺失不会让评测器崩溃：`contract.py` 的各 `from_obj` 对缺字段一律取默认值（宽容解析）。
- 但**缺字段会直接拉低对应指标 / 触发闸门**（例如没有 `restore` → `restore_verified = False`）。
- 因此「运行包填得全不全」直接决定分数，**这是执行侧的责任**。

> 完整示例见 `evaluation/fixtures/run-bundle/case-01-slow-query-fullscan.json`（8 个用例各一份金标准运行包）。

---

## 4. 评测器明确**不做**的事

以下全部属于**执行 / 采集侧**，评测器一行都不做：

- 启动 `docker compose` / 目标服务、执行 `start_command`、等 `healthcheck`；
- 应用或回滚被测代码改动（patch）；
- 跑 `load_profile` 压测、造数据、抓取慢查询日志；
- 调用被测 Agent、记录其**轨迹（trajectory）**与工具调用；
- 采集**制品（artifacts）**、计算校验和、判定可读性；
- 独立**复测**、判定业务断言；
- 采集**成本**（墙钟 / 工具调用次数 / 制品字节数）。

评测器只做一件边界内的核心事：**把上述已采集到的结构化成运行包，翻译成指标、闸门、总分与报告。**

## 5. 责任边界

```
┌────────────────────────── 执行 / 采集侧（非本方范围）──────────────────────────┐
│  原始代码 + 修改后代码                                                        │
│      │  启动服务 · 应用改动 · 压测 · 采轨迹/制品/成本 · 复测                    │
│      ▼                                                                        │
│  运行包  runs/<case-id>.json   ──────────  ← 唯一的交接物（接口边界）           │
└───────────────────────────────────┬───────────────────────────────────────────┘
                                     │  只消费，不生产
┌────────────────────────────────────▼──────────────────────────────────────────┐
│  评测 / 判分侧（本方交付：datasets/）                                          │
│  run_eval.py ── contract.py · metrics.py · scores.py                          │
│      │  读运行包 → 算指标 → 判闸门 → 聚合 → 出报告                              │
│      ▼                                                                        │
│  report.json / report.md   （结论 · 证据 · 过程 · 成本 · 总分）                 │
└───────────────────────────────────────────────────────────────────────────────┘
```

| 事项 | 执行/采集侧 | 评测侧（本方） |
| --- | :---: | :---: |
| 制定用例、缺陷标注、金标准（`case.json`） | | ✅ |
| 制定评估方法 / 指标定义 / 打分流程 | | ✅ |
| 产出「运行包」原始测量数据 | ✅ | |
| 指标计算 / 闸门 / 总分 / 报告 | | ✅ |
| 结构校验 + 隔离守卫 + 基线可复现 | | ✅ |
| 启动 SUT / 跑实验 / 采轨迹 | ✅ | ❌（永不触碰） |

## 6. 常见误解澄清

| 误解 | 事实 |
| --- | --- |
| 「把两份代码丢给评测器，它就会自动跑对比实验并给分」 | ❌ 它不会跑实验。你须先跑出运行包，它才有分可判。 |
| 「评测器会自己启动服务、压数据库」 | ❌ 评测器仅用标准库做数据计算，代码里**不存在**任何启动进程 / 调 SUT 的路径。 |
| 「运行包随便填，评测器会自动补全」 | ❌ 缺失字段按默认值（多为「未达标」）处理，直接影响得分与闸门。 |
| 「分数不高就是评测器有问题」 | 先查运行包是否填写完整、轨迹/制品/回滚是否采集到位；判分链本身有金标准回归测试兜底。 |
| 「评测器会把结论写进 SUT 或读取金标准」 | ❌ 有 `guard_sut_separation.py` 与 `isolation_guard.py` 两道守卫断言双向隔离。 |

## 7. 想跑一轮评估，怎么配合

**方式 A：执行侧自己产运行包（推荐）**
1. 执行侧按第 3 节的键结构，为每个用例产出 `runs/<case-id>.json`；
2. 评测侧执行：
   ```powershell
   python evaluation/run_eval.py --runs runs --out out
   ```
3. 读 `out/report.json`、`out/report.md`。

**方式 B：借助采集模块（仍不跑实验）**
`evaluation/collect_run_bundle.py` 提供「原始代码 + 修改后代码 → 运行包」的**统一接口与组装/校验**能力：

- 它把「需要哪些参数、如何组织」固化成契约，并做**完整性 + 溯源（代码指纹）+ 校验**；
- **真正跑实验的动作由可插拔的「采集后端」完成**；本模块内置的后端只做「读取既有测量 + 组装」，**不含任何调用 SUT 的代码**。
- 与执行侧的协作边界见 `docs/运行包采集模块交接说明.md`。
