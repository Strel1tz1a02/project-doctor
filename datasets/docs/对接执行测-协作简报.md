# 对接执行测 · 协作简报

> 本文件是**数据集侧（判卷机）**与**执行测侧（执行器）**双方 AI 进行**信息概要交互**的唯一约定载体。
> 双方都在**同一份文件**里追加条目，不另开分支文件、不各写一份。
> 文件路径：`datasets/docs/对接执行测-协作简报.md`（随 `datasets/` 一并版本管理）。

---

## 0. 双方角色与红线（任何条目都不得违反）

| 侧 | 角色 | 权限 | 红线 |
| --- | --- | --- | --- |
| 数据集侧 | **判卷机**：评估方法 + 评估数据集 | 只读 `datasets/` 金标准；改评分器 / 数据集 / 文档 | **绝不调用 / 运行被测 Agent（SUT）**；不打补丁、不跑实验、不启动服务 |
| 执行测侧 | **执行器**：跑被测 Agent、采集运行包 | 调用 SUT、产出运行包 JSON | 只**消费**数据集与契约；不改 `datasets/` 下的金标准与评分器 |

- 数据集侧只消费运行包 JSON（run bundle），据此评分；执行侧只按契约产出运行包。
- 运行包中 `retest.repair` 的**语义由数据集侧定义**，**实际数据由执行侧采集提供**。
- `datasets/` 为只读金标准；SUT 源码与 `project/` 内**一律不得引用**本目录（CI 强制）。

## 1. 交互协议（同一份文件怎么用）

1. **只在「§4 信息交换记录」追加**，不倒序改写历史条目；如需更正，新增一条并注明 `更正 #<被更正条目号>`。
2. 每条目固定格式（**概要级**，不贴大段原始日志）：

   ```text
   ### [序号] <YYYY-MM-DD> · <数据集侧 | 执行测侧> · <主题>
   - **结论**：一句话结论。
   - **依据**：文件 / 字段 / 命令 / 数值等可核验依据。
   - **影响面**：影响哪些用例 / 指标 / 契约字段。
   - **请求对方**：需要对方做什么（无则写「无需动作」）。
   - **状态**：`待确认` / `已闭环` / `阻塞`。

3. **需要对方拍板的事项**，一律登记到「§5 开放事项」表格，并在条目里引用其 `ID`。
4. **契约变更**（字段增删、闸门/适用数变化、期望结论口径）必须：先登记开放事项 → 双方确认 → 才改代码/数据 → 条目里附回归证据。
5. 双方**只交换概要**：原始运行包、长日志、截图走外部链接或路径引用，不入正文。

## 3. 当前契约快照（截至最后一次条目更新）

### 3.1 运行包结构

```text
{
  baseline,      # 基线观测
  report,        # 被测 Agent 的诊断报告（decision / findings / reason / limitations ...）
  trajectory,    # 过程轨迹
  retest,        # 复测块（见 3.3）
  artifacts,     # 制品清单
  restore,       # 环境回滚
  cost           # 成本
}
```

- 顶层可用 `runs` 列表表达**单用例多次运行**（评分器 `_case_runs` 拆包、`merge_case_results` 聚合）。

### 3.2 `expected.decision` 取值与语义

| 取值 | 语义 |
| --- | --- |
| `verified` | 期望 Agent 能凭**结构化证据**证实唯一根因 |
| `lead` | 期望 Agent 给线索但**不强行 verified**（缺陷真实但不可证实 / 类型暂不支持） |
| `unclassified` | 证据不足场景应**如实声明**、不冒充结论 |

### 3.3 `retest` 块与修复记录（执行侧采集）

```text
retest = {
  "performed": bool,
  "improvement_percent": float | null,
  "business_assertions_passed": bool,
  "repair": {                     # RepairRecord，缺省按「未尝试改动」处理
    "attempted": bool,            # 是否尝试改动
    "patch_present": bool,        # 是否真的产出补丁
    "patch_files": [ {"path":..., "line":...} | {"files":[...]} ],  # 补丁位置
    "gain_attributable": bool     # 收益是否可归因于本次补丁
  } | null
}
```

> 若用例显式声明了 `expected.repair` 但运行包缺失 `retest.repair`，评分器**按未达标处理**（不跳过）。

### 3.4 指标与硬闸门

- 指标总数 **28** = 用例级 21 + 步骤级 7（`group="step"` 不进入总分与硬闸门，仅作归因）。
- 用例级含 **4 项修复能力指标**：`repair_warranted` / `repair_target_hit` / `repair_restraint` / `gain_attributable`。
  - 均为 BOOLEAN、结论层、`applies_to = normal ∪ boundary`（**不进 failure**）。
  - **仅当用例显式声明 `expected.repair` 时才产出取值**，未声明者不评估以免污染存量总分。
- 指标**适用数**：`normal=26`、`boundary=27`、`failure=15`（failure 不含 `root_cause_recall` 等）。
- 硬闸门（`_build_gates`）：
  - normal → 9 项常规闸门；
  - boundary → `false_verified=false` + `limitation_declared=true`；若 `expected.decision==verified`，**并入 normal 常规闸门**；若为 `lead` 追加 `decision_exact`；
  - failure → 4 项；
  - **重构闸门**：仅当 `expected.repair` 已声明且已产出 `repair_warranted` 时，并入 4 项 `_repair_gates`。
- 全局硬门槛：`false_verified` 为乘性门槛（`RewardProfile.hard_gate_metrics = ("false_verified",)`）。

### 3.5 SUT 问题类型能力边界（判卷依据，非我方能力）

- 目前**可产出 `verified`** 的问题类型：`slow_query`、`n_plus_one`、`deep_pagination`。
  - 依据：`Finding.verified_requires_structural_evidence` 要求 `status=="verified"` 且 `kind ∈ {slow_query, n_plus_one, deep_pagination}`，且 `experiment_ids / sql_call_ids / code_locations / evidence_refs / excluded_explanations` 非空、`recommendation is not None`。
- 其余 6 类（`connection_pool` / `large_response` / `connection_setup` / `excessive_logging` / `config_regression` / `thread_pool`）**暂不可能产出 `verified`**，相关用例期望 `decision=lead`。

### 3.6 金标准回归基线（`evaluation/test_golden_bundle.py`）

- `GOLDEN_CASES_EVALUATED = 14`、`GOLDEN_FALSE_VERIFIED = 0`、`GOLDEN_MEAN_TOTAL = 0.8762`。
- `case-07-n-plus-one-order-user` 期望 `verified`，其金标准 `total = 1.0`。
