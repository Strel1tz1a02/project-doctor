# 数据集使用说明

`Datasets/` 是后端性能诊断 Agent（`project-doctor`）的评估数据集。每个数据单元都是一个带已知缺陷、可独立构建运行的后端项目，外加一张记录 ground truth 的问题卡。组员用它出题与评分，被测 Agent 在评估时只接触其中的 `project/` 目录。

这份文档给两类人看。**组员**（数据维护者、评估执行者）关心怎么新增用例、跑校验、产出评分报告；**Agent**（被测的诊断模型）关心自己会被投喂什么、要产出什么、按什么标准被判定。若只想了解字段与目录约定，读《[数据集结构规范](docs/数据集结构规范.md)》；若只想知道指标怎么算、三类样例怎么判定，读《[Agent 评估方法](docs/Agent评估方法.md)》。

## 环境与快速开始

评测侧（校验、评分）只需要 CPython 3.10 及以上，全部用标准库实现，无需安装任何第三方包。真正启动被测项目时，另外需要 JDK 17、Maven 与 Docker（MySQL 8.0）。

在 `Datasets/` 目录下依次执行：

```bash
python tools/validate_cases.py        # 校验所有 case.json 是否符合 schema
python tools/isolation_guard.py       # 断言答案隔离没有被破坏
python evaluation/run_eval.py         # 评测器自检：七步流程、三类聚合、全局门槛
python evaluation/run_eval.py --runs evaluation/fixtures/run-bundle --out evaluation/out
```

最后一条用 `fixtures/run-bundle/` 中的金标准运行包跑完全部用例，并在 `evaluation/out/` 生成 `report.md`（人读）与 `report.json`（机读）。上述四条命令的退出码都是 0 表示通过，非 0 表示存在问题。金标准运行包当前已覆盖全部 8 个用例（`case-01`~`case-08`），因此该命令不会出现 `cases_missing_bundle`；若后续数据集继续新增用例而尚未配套运行包，可加 `--only-bundled` 让评测器跳过缺包用例、只对已有运行包的用例做回归。

## 数据集的构成

一个数据单元就是一个目录，目录名等于 `case_id`：

```text
Datasets/
├─ README.md                    # 数据单元索引
├─ 使用说明.md                  # 本文件
├─ docs/                        # 规范与方法文档
├─ _schema/case.schema.json     # 问题卡的 JSON Schema
├─ tools/                       # 校验脚本与答案隔离守卫
├─ evaluation/                  # 评测器、单测与金标准运行包
└─ <case-id>/
   ├─ case.json                 # 问题卡（ground truth，评测方资产）
   ├─ README.md                 # 用例维护者文档（含答案，评测方资产）
   └─ project/                  # 被测项目，唯一暴露给 Agent 的目录
```

`docs/`、`tools/`、`evaluation/`、`_schema/` 以及任何以 `_` 开头的名字是保留项，不被视作数据单元。

数据集同时承担两种角色，理解这一点是理解所有约定的前提：它既是 Agent 的**输入**（症状描述加一个可运行项目），也是评分时 **ground truth 的唯一来源**。前者要求 `project/` 尽量贴近真实、可复现；后者要求答案绝不外泄。二者通过物理隔离共存——元数据放在 `case.json`，项目实物放在 `project/`。

## 用例覆盖矩阵与统计

当前收录 8 个用例，共用 Spring Boot 3.2.5 + MyBatis + MySQL 8.0 技术栈，覆盖正常、边界、失败三类判定：

| case_id | 类型 | 问题类型 | 难度 | 期望结论 | 表征症状 | 主缺陷 |
| --- | --- | --- | --- | --- | --- | --- |
| `case-01-slow-query-fullscan` | `normal` | `slow_query` | easy | `verified` | `GET /api/orders/recent` P95 超 300ms | `orders` 缺 `(status, created_at)` 复合索引，全表扫描 + filesort |
| `case-02-slow-query-composite` | `boundary` | `slow_query` | hard | `lead` | `GET /api/orders/search` P95 超 2s | 同一项目叠加前导通配符、N+1、冗余 COUNT、深分页，仅复合索引可证实 |
| `case-03-slow-query-unreproducible` | `failure` | `slow_query` | medium | `unclassified` | 工单称偶发 P95 超 800ms | 无可证实缺陷；`orders` 已具备复合索引，其余为干扰项 |
| `case-04-slow-query-user-index` | `normal` | `slow_query` | easy | `verified` | `GET /api/orders/by-user` P95 超 300ms | `orders` 除主键外无任何索引，按 `user_id` 过滤即全表扫描 |
| `case-05-slow-query-skewed-status` | `boundary` | `slow_query` | medium | `lead` | `GET /api/orders/recent` 部分取值下 P95 超阈值 | 缺 `(status, created_at)` 复合索引，但收益随 `status` 分布倾斜而波动，难以稳定证实 |
| `case-06-slow-query-undersized` | `failure` | `slow_query` | medium | `unclassified` | 声称慢，但仅 300 条订单 | 缺陷真实（缺索引），但数据规模不足，任何实验都无法证实收益 |
| `case-07-n-plus-one-order-user` | `boundary` | `n_plus_one` | medium | `lead` | `GET /api/orders/recent?size=200` 延迟随条数线性增长 | `for` 循环逐条查用户，形成 `1+size` 次数据库往返，单条 SQL 无计划问题（等待 Agent 支持） |
| `case-08-deep-pagination-large-offset` | `boundary` | `deep_pagination` | medium | `lead` | `GET /api/orders/page?page=10000` 深页 P95 显著升高 | `LIMIT offset, size` 大偏移需扫描并丢弃近 20 万行，索引已存在、无需补索引（等待 Agent 支持） |

### 覆盖统计

按各维度统计用例分布，用于核对判定谱系是否均衡：

| 维度 | 取值与数量 |
| --- | --- |
| `case_type`（判定谱系） | `normal` ×2（`case-01`、`case-04`）、`boundary` ×4（`case-02`、`case-05`、`case-07`、`case-08`）、`failure` ×2（`case-03`、`case-06`） |
| `problem_kind`（问题类型） | `slow_query` ×6（`case-01`–`case-06`）、`n_plus_one` ×1（`case-07`）、`deep_pagination` ×1（`case-08`）；枚举另预留 6 类**待补**（见下） |
| `difficulty`（难度） | `easy` ×2（`case-01`、`case-04`）、`medium` ×5（`case-03`、`case-05`、`case-06`、`case-07`、`case-08`）、`hard` ×1（`case-02`） |
| 期望结论 `decision` | `verified` ×2（`case-01`、`case-04`）、`lead` ×4（`case-02`、`case-05`、`case-07`、`case-08`）、`unclassified` ×2（`case-03`、`case-06`） |
| `reward_profile`（评分档） | `normal_single` ×2、`boundary_composite` ×4、`failure_honesty` ×2 |

三条覆盖约束：每个 `case_type` 至少 2 个用例；`case_type` 与期望结论一一对应（`normal`→`verified`、`boundary`→`lead`、`failure`→`unclassified`）；`slow_query` 已铺满 6 个变体，`n_plus_one` 与 `deep_pagination` 各预置 1 个，受 Agent 契约限制其期望结论只能是 `lead`（见《数据集结构规范》「现状提示」）。

问题卡的 `problem_kind` 枚举已一次性预留对齐设计文档的**全部 9 类**，当前仅 3 类落地，其余 6 类（`connection_pool` / `large_response` / `connection_setup` / `excessive_logging` / `thread_pool` / `config_regression`）为**待补**，暂无对应用例。取值域与逐类覆盖现状见《数据集结构规范》「problem_kind 取值与覆盖现状」。

### 对照设计

这些用例并非彼此孤立，而是刻意构成的对照组：

- **单缺陷 vs 组合缺陷**：`case-01` 是 `case-02` 的单缺陷版本——两者底层是同一个缺复合索引的项目，`case-02` 额外叠加前导通配符、N+1、冗余 COUNT、深分页等干扰项，只有复合索引能被单变量实验证实。
- **有索引 vs 无索引**：`case-03` 的数据规模与接口同 `case-01` 一致，只差一个复合索引是否存在——`case-03` 已具备该索引、无可证实缺陷，用于检验 Agent 是否会因「表象慢」而编造根因。
- **规模充足 vs 规模不足**：`case-06` 与 `case-04` 保留相同的真实缺陷（缺索引），但 `case-06` 仅 300 条订单，同一缺陷「真实但不可证实」，用于检验 Agent 会不会对不可证实的缺陷强行下结论。
- **同缺陷、不同过滤路径**：`case-04`、`case-05` 是缺索引的另外两个变体，分别在 `user_id` 过滤、`status` 分布倾斜下展开，覆盖不同证实难度。
- **表象相似、机制不同**：`case-07`（N+1 往返放大）与 `case-08`（深分页大偏移）都表现为「列表/分页接口慢」，但根因都不在单条 SQL 的计划上、且索引已存在，用于检验 Agent 不把「有慢查询症状」一律误判为「缺索引」。

把 8 个用例放在一起，能把 Agent 的行为区分成三类——**能证实唯一根因**（`verified`）、**只能给线索但不越级下结论**（`lead`）、**证据不足时拒绝编造根因**（`unclassified`）。评测方最看重的不是「答得快」，而是「该不下结论时绝不下结论」。

## 什么对 Agent 可见

答案隔离是这个数据集的硬约束。`case.json` 里的 `defects`、`expected` 是评测方资产，绝不能被被测模型读到。评估运行时只把 `case-<id>/project/` 挂给 Agent，`case.json`、用例级 `README.md`、`docs/`、`_schema/` 一律隔离。

这条铁律不靠自觉维护。`tools/isolation_guard.py` 会扫描每个 `project/`，一旦发现敏感文件、越界符号链接、版本库目录，或文本内容引用了 `case.json`、`_schema`、`Datasets/docs`、`ground truth`、`root_cause_ids` 等答案资产，就判定为泄漏并退出码 1；`.github/workflows/validate-cases.yml` 在每次变更时强制执行。新增或改动用例后务必本地先跑一遍。

## 面向组员

### 校验与守卫

把数据单元当作代码来管理，改动后两件事必做。

```bash
python tools/validate_cases.py        # 校验全部；也可只传某个 case.json
python tools/validate_cases.py path/to/case.json --json --quiet
python tools/isolation_guard.py       # 隔离检查；--json 输出机器可读结果
```

`validate_cases.py` 内置一个聚焦子集的 JSON Schema 校验器（环境里没有 jsonschema），覆盖 `_schema/case.schema.json` 实际用到的关键字。退出码 0 通过、1 校验失败、2 用法或 schema 自身错误。

### 运行评估

评测器把一次完整评测拆成七步：冻结评测器版本、加载并校验用例、采集基线（重复至少 3 次）、把 `project/` 交付给 Agent、自动评分、独立复测、聚合出总体报告。编排入口是 `run_eval.py`：

```bash
# 自检：不接触真实用例，验证流程与聚合逻辑
python evaluation/run_eval.py

# 对一组运行包评分
python evaluation/run_eval.py --runs evaluation/fixtures/run-bundle --out evaluation/out

# 指定用例根目录（默认扫描仓库内的数据单元）
python evaluation/run_eval.py --runs <运行包目录> --out <输出目录> --cases-root <用例根>
```

`--runs` 指向一个运行包目录，其中每个用例对应一个 JSON，文件名即 `case_id`。运行包记录一次真实评测所需的全部原始数据，字段固定为 `baseline` / `report` / `trajectory` / `retest` / `artifacts` / `restore` / `cost`。`evaluation/fixtures/run-bundle/` 下的八个文件是 `case-01`~`case-08` 的金标准运行包（覆盖 normal / boundary / failure 三类），既是回归测试数据，也是运行包格式的可读范例——按用例类型挑选对应的范例照抄结构即可（normal 看 `case-01`/`case-04`，boundary 看 `case-02`/`case-05`/`case-07`/`case-08`，failure 看 `case-03`/`case-06`）。

评测器按用例类型自动选择适用的指标与硬闸门，也支持单独调用各层：

```bash
python evaluation/metrics.py          # 四层指标自检
python evaluation/scores.py           # 评分数据模型自检
python -m unittest discover -s evaluation -p "test_*.py"
python -m unittest discover -s tools -p "test_*.py"
```

### 新增一个用例

新建用例时，目录名遵循 `case-<两位序号>-<问题类型>-<变体>`，全小写连字符分隔；目录内放齐 `case.json`、`README.md`、`project/` 三件套。问题卡字段与验收要求以《数据集结构规范》为准，其中几条最容易被忽略：

- `primary` 缺陷只能有一个，且必须能被平台唯一允许的单变量实验（`baseline` 对照 `candidate_index`）区分；一个改动同时牵动多个缺陷时应拆成多个用例。
- 每个缺陷都要有稳定唯一的 `path:line`，且相对 `project/` 的路径。
- 边界与失败用例必须写 `expected.limitations_required`，缺项即判不合格。
- `case-03` 这类「表象慢但无可证实缺陷」的用例，`expected.root_cause_ids` 枚举的是用例承认存在、但不可证实的候选缺陷目录，不是要求 Agent 命中的根因。

入库前对照《数据集结构规范》末尾的验收要求逐条自查（可复现、单变量可控、定位确定、正确性可断言、答案隔离、环境可恢复），再更新根 `README.md` 的数据单元索引，最后跑一遍上文两条校验命令。

## 面向 Agent

### 输入

Agent 收到的是问题卡中不含答案的那部分，以及一个可运行项目：

- 症状：`symptom.summary`、`symptom.endpoint`、`symptom.target_metric`，即「哪个接口、什么现象、看哪个指标」。
- 运行方式：`runtime.start_command`、`runtime.healthcheck`、`runtime.load_profile`（并发数、时长、预热）。
- 数据情况：`dataset_profile` 描述的测试数据规模与缓存状态。
- 项目实物：`project/` 内的源码、构建脚本、建表脚本与初始化数据。

Agent 拿不到 `defects` 与 `expected`。它需要自己测量基线、提出竞争假设、设计单变量区分实验、定位代码、给出带证据的结论。

### 期望产出

Agent 的输出对齐 `project-doctor` 的产出契约（详见《数据集结构规范》里的字段映射表）。关键几点：

- 每条结论用 `Finding` 表达，`status` 在 `verified` / `lead` / `refuted` / `unclassified` 中取值。
- 命中的代码位置用 `Finding.code_locations` 给出，含 `commit`、`path`、`line` 与 `association_evidence_ids`，每条位置都要带佐证。
- 想主张性能改善，必须给出经复测的 `Recommendation.measured_gain_percent`，且只有在 `validation_status=retested` 时才可信；估算值不能冒充实测。
- 影响度量用 `Impact.method` 标注来源，`intervention` 是唯一可信的方式。
- 边界与失败场景，用 `Finding.limitations` 声明结论的适用范围与不确定之处。
- 业务正确性通过 `Observation.business_valid` 断言，用于判断修复是否破坏功能。

### 评分要点

评分围绕结论、证据、过程、成本四层展开，硬闸门按用例类型区分。全局铁律只有一条：**误验证必须为 0**。凡是把没有证据的东西标成 `verified`，无论整体结论多漂亮，该轮直接判负——宁可漏判，不可错判。

- 正常用例（`case-01`、`case-04`）：结论精确为 `verified`、命中期望根因与代码位置、证据完整、改善达标、正确性未被破坏，任一不满足即不通过。结论若降级为 `lead`，按漏判单独统计。
- 边界用例（`case-02`、`case-05`、`case-07`、`case-08`）：结论须为 `lead`，且必须声明 `limitations_required` 列出的限制项，不得对被排除的解释下 `verified`。这类用例不要求复测。
- 失败用例（`case-03`、`case-06`）：不得产生任何 `verified` finding，整体结论须为 `unclassified` 且如实声明证据不足，也不得断言候选目录之外的根因。

四层指标的具体定义、阈值与聚合口径见《[Agent 评估方法](docs/Agent评估方法.md)》。基础环境限制也直接影响判定：Agent 契约当前只支持 `slow_query` 与 `unclassified` 两种 `ProblemKind`，因此 N+1 与深分页相关缺陷在 Agent 扩展类型之前不可能产出 `verified`，对应用例的期望结论据此标注为 `lead` 或 `unclassified`。问题卡的 `problem_kind` 枚举虽已预留 9 类，但 Agent 侧仍未覆盖其中 6 类，日后为这些类型补写用例时期望结论同样只能标 `lead` / `unclassified`。

## 常见问题

**评测器报 `ModuleNotFoundError`？** 评测侧只用标准库，出现第三方依赖报错说明解释器选错了，确认 `python --version` 不低于 3.10。

**`isolation_guard.py` 报某文本引用了 `case.json`？** 多半是 `project/README.md` 或初始化脚本里带了「答案」字样。把它改成只描述现象，不描述根因，再重跑。

**`run_eval.py` 提示某用例缺运行包？** 运行包文件名必须严格等于 `case_id`。参照 `evaluation/fixtures/run-bundle/` 补齐 `baseline` / `report` / `trajectory` 等必备字段。

**基线复测不可复现要修吗？** 不一定。`case-03` 的基线本就波动（相对离散度远超 10% 的运行 / 复测口径），这正是失败用例的设定，失败用例的判定只要求如实记录、不要求可复现。注意「验收口径 ≤ 25%」与「运行 / 复测口径 ≤ 10%」是两个各自命名的概念：前者是用例入库要求，后者是单次运行的测量可信度判据。

**新增问题类型（如 N+1、连接池、大响应）现在能用吗？** 问题卡的 `problem_kind` 枚举已一次性预留设计文档划定的 **9 类**（`slow_query` / `n_plus_one` / `connection_pool` / `deep_pagination` / `large_response` / `connection_setup` / `excessive_logging` / `thread_pool` / `config_regression`），可按规范先行编写归档，其中尚未落地的 6 类为**待补**。但在 `project-doctor` 扩展 `ProblemKind` 之前，这些非 `slow_query` 用例的期望结论应标为 `unclassified` 或 `lead`，并在 `evaluation.notes` 写明「等待 Agent 支持」。
